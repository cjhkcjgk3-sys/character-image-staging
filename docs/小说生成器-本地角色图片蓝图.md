# 小说自动生成器：本地角色图片蓝图

**状态：审阅稿，等待用户确认。**本文规划在现有小说自动生成器中增加可选图片能力；当前没有改造生成器，也没有在手机上安装或验证新功能。中转站现已改为只使用各作品的 `00-清单.md`，不再使用 `catalog.json`；下文已按此调整。

## 1. 要实现的体验

Agent 将角色图片整理到 GitHub 中转站，用户在网络方便时把图片 ZIP 保存到手机。之后在小说自动生成器里一次选择 ZIP，图片导入插件管理的本地图片库；批量写卡时，生成器根据当前角色逐张取图，连同当前提示词一起发给同一个模型。换角色时，清理上一轮的临时图片，图片库原图保留。

```text
Agent 收图 → GitHub 图片中转站 → 下载作品包到手机
                                      ↓
                   小说生成器：一次导入 ZIP → 本地图片库
                                      ↓
名单逐人生成 → 按当前角色取图 → 本轮请求送图 → 当前模型直接看图
                                换角色清理临时图    ＋现有文字联网搜索
                                图片库原图保留
```

一部作品可以有一百多位角色；第一版不把功能限定在原神，也不按角色逐张要求手动上传。用户的角色名单、提示词、模型和联网方式继续沿用。

## 2. 已确定、建议与待验证

- **已确定**：以现有小说自动生成器为主；GitHub 只做图片中转；手机一次选择 ZIP 导入本地图片库；生成时不逐张从 GitHub 下载。逐角色将图片本身作为多模态输入，换角色清理临时图，图片库原图保留。
- **已确定**：图片文件以中文角色名命名，按作品组织；以人物能否辨认为准，大小 500 KB 至 2 MB。`00-清单.md` 是唯一数据，勾选表示已收集。名字匹配会规范化全角半角、空白、间隔点和作品前后缀，并比较链接文本、别名和文件名。
- **建议，供本次审阅**：增加一个默认关闭的“自动附上角色图片”开关和“导入本地 ZIP”入口；启用后自动处理正常批量、换人和重生成。自动添加的角色图片不长期保存在聊天记录中，已有无图功能保持原样。
- **待验证**：手机实际安装的生成器版本、SillyDroid 的文件选择器与保存接口、模型当前图片内联配置、图片和联网搜索同时工作，以及真正发出的请求内容。
- **暂不做**：新建独立酒馆插件、在线逐张搜图或每轮访问 GitHub、改写模型 API/搜索代理、批量生成图片文字描述、修改酒馆视觉白名单。

## 3. 用户怎么操作

在小说生成器现有“生成设置”中增加一小块：

```text
角色参考图片
[ ] 自动附上角色图片
[导入本地 ZIP]   已导入：若干  待确认：若干
                   [查看待确认或失败项]
```

1. 用户在手机一次选中一个 ZIP，包里可以有一个或多个作品文件夹。首版不增加单独选择文件夹或多选图片的入口；正常导入后不需要逐角色再选文件。
2. 插件读取 `00-清单.md` 和图片，显示进度和结果；已勾选且文件合格的项目自动处理，未勾选、有歧义或文件不合格的项目集中显示。
3. 用户开启“自动附上角色图片”，在原有名单框输入角色并开始生成。插件按顺序为每轮取图，并在面板显示当前角色及图片预览；换角色时清理上一轮临时图，图片库中的原图始终保留。
4. 找不到图片或目标不唯一时，提示缺少图片，本轮只写卡不附图，不得悄悄用上一位角色的图。用户仍可随后补充图片或确认别名。

图片功能关闭时，不改变原有的纯文字批量写卡、续写、暂停、恢复、结果隔离及导出。

## 4. 本地导入与保存

### 4.1 标准作品包

优先支持中转站作品文件夹打成的 ZIP：

```text
原神.zip
└── 原神/
    ├── 00-清单.md
    ├── 温迪.jpg
    └── 芙宁娜.webp
```

`00-清单.md` 是唯一数据。已勾选且链接到合格图片（JPEG、PNG 或 WebP，大小 500 KB 至 2 MB，位于本作品文件夹内）的条目可直接使用。未勾选的条目不自动用于生成。别名写在「别名：」后面。人看的任务清单和图片放在同一作品文件夹。

只把符合条件的图片作为图片导入；`00-清单.md` 等文本不当作图片。拒绝绝对路径或 `..` 越界路径，不能用压缩包内的路径直接覆盖酒馆其他文件。

当前原神样本有 8 张图片：温迪、钟离、雷电将军、纳西妲、玛薇卡、安娜丝塔夏已勾选；芙宁娜、芙卡洛斯因小于 500 KB 未勾选。**勾选表示已收集且可通过检查的图片；未勾选不自动用于生成。**

### 4.2 没有清单的普通 ZIP

有些 ZIP 只包含 `原神/温迪.jpg` 这样的作品文件夹和图片，没有 `00-清单.md`。仍然只需选一次 ZIP：插件根据包内可用的文件夹名和中文图片文件名建立本地对应；无法获知作品时询问作品名，不要求用户回头联网或手工编写清单。

普通 ZIP 中的图片按本地提供的参考图处理，不虚构官方来源或原作版本。能够唯一对应的角色自动建立映射；同名、版本不清的条目列入待确认。信息不足时，允许用户在已导入的候选中选择并记住对应关系，不强制重新命名。

### 4.3 存储和重复导入

- 插件界面提供自己的“本地图片库”；物理文件使用酒馆自身的图片保存接口，存进该酒馆用户的图片目录中由插件管理的范围，而不是写进插件代码安装目录或 GitHub。插件设置只保存名称、版本、本地路径、哈希和用户选择等小型索引，不保存整张图片或 Base64。此安排旨在让普通插件更新不覆盖图片，实际升级与设备迁移仍需验证。
- 按作品区分图片；中文角色名保持可读。相同内容重复导入时复用已有文件；同名但内容不同或无法安全判断时先保留已有文件并提示，不覆盖用户已有图片或聊天附件。
- 切换角色、生成结束、停止或失败时，均不删除图片库原图；同一张图可在以后重新生成角色时再次使用。
- 手机下载的 ZIP 和导入后的图片库是两份独立存储。导入功能在手机验收通过、图片核对无误后，可自行删除手机下载的 ZIP 释放空间；以后新增图片可再导入一个 ZIP。清除酒馆应用数据或迁移手机前，应先备份图片库或保留可重新导入的图片包。
- 单张保存成功并核对后才更新该张的索引。导入中断时保留已完成项，重新选择同一个包后跳过已完成项；浏览器刷新后可能需要用户重新选包。
- 导入时显示成功、待确认、失败数量。逐张处理和及时释放临时图片数据；ZIP 解析本身可能占用整包内存，约百名角色的大包需在手机上验证。如果现有解析库内存不足，优先评估插件本地提供的低内存或流式解析方式；首版的正常流程仍以一次选择一个 ZIP 为目标，设备无法处理时应明确提示，不能默称导入成功。

## 5. 名字查找

保留名单原文和图片原中文名。匹配前先规范化：去掉首尾空白，统一全角与半角，去掉空格和间隔点，并去掉作品前缀或后缀。因此 `原神·温迪`、`原神-温迪`、`温迪（原神）`、`温迪(原神)`、`【原神】温迪` 都视为 `温迪`。插件依次尝试：

1. 与清单链接文本、别名、图片文件名（不含扩展名）比较。
2. 仍没有结果时，若某一条能唯一地互相包含，也可以匹配。
3. 没有结果或有多条可能时，提示缺少图片，只写卡不附图，不静默选错图，也不沿用上一角色的图。

该规则已在中转站 `tools/check.py` 的 `normalize_name` 与 `match_name` 中实现，以后可直接移植。不从整段提示词里随意猜当前角色。两种查找方式是待开发功能，不要求用户为了兼容而重复放图或修改原名单。

## 6. 每一轮怎样送图

1. 从生成器当前任务取得完整角色名。普通批量、指定角色重生成和候选预览重生成都显式传入该轮角色名，不能只依赖名单当前位置。
2. 在本地索引中匹配角色及形象，先实际读取本地图片。把角色、聊天、当前尝试和图片绑定为本轮临时状态；读取失败就在发送前中止，改为只写卡不附图。
3. 复用生成器现有的生成入口和拦截链，在酒馆组装请求前向**本次请求的消息副本**加入该图片；角色文本替换仍按现有生成器流程进行，图片模块不额外改写聊天正文，也不永久替换原消息的附件。
4. 原有用户附件按原有方式保留；如果原消息是图库模式，仍保留原来选中的媒体，再加入本轮角色图。插件只负责本轮自动添加的图片；用户原来已有图片时，模型也可能一并收到它们。
5. 本轮可以使用读取后在内存中生成的图片数据 URL，避免酒馆二次取图失败时只记录日志并跳过图片；图片数据不写入聊天、插件设置或日志。酒馆以图片附件处理该数据，并与当前提示词一起交给所选模型；联网开关和搜索工具继续由用户当前配置决定。成功、失败、停止、换角色或切换聊天后清理本轮临时状态，下一轮重新取对应图片。

优先让插件自动添加的图片只存在于本次请求副本中：发送完清理临时数据，聊天记录无需长期保存这张自动图片，也不会因切换角色删除图库原图。如果目标宿主只能通过聊天临时附件实现，必须先验证能够只移除插件这次添加的引用，不删除底层图库文件或用户原有附件；无法安全做到就暂停并提示。

酒馆通常将图片文件保存在用户图片目录，聊天附件记录的是图片路径，因此聊天显示图片并不一定意味着又存了一份同样大小的文件。本方案仍按用户要求避免长期保存自动图片的聊天引用，以免多余记录或角色图片混用。

现有 1.19.0 源码在生成前构造的 `coreChat` 是**浅拷贝**：实现时必须复制要改的 `extra` 和 `media`，不能直接修改共享数组。生成器已有 `NovelGen_isolateRoleResult` 拦截器，图片功能需与它组合，不能覆盖原有结果隔离；隔离开启或关闭都应能送图。

酒馆会捕获拦截器异常并可能继续生成，因此找不到图片、无法识别本轮消息或图片附加失败时，必须明确中止本轮附图并将原因反馈给生成器，不能只抛异常后悄悄发纯文字却不说明。实际消息副本、图库处理、停止和错误回传均须在目标宿主实测。

启用图片功能时，应优先使用当前酒馆实际提供的能力判断，核对媒体内联和当前模型是否可用；不再维护一份新的模型名称白名单。明确不支持或无法可靠确认时提示原因并阻止本轮图片生成，用户仍可关闭图片功能使用原有文字流程。能力判断通过也需要实测请求，不能仅凭开关认定模型收到了图片。

## 7. 版本与质量边界

- 目标环境是用户报告的 SillyDroid／SillyTavern 1.19.0；当前使用 Chat Completion，来源为 Google Vertex AI 和自定义 OpenAI 兼容接口。实际手机所装生成器版本及后续补丁尚未读取。
- 酒馆图片上传接口和本地 ZIP 库在公开 1.19.0 源码中存在；ZIP 库是否在手机安装包中可用要探测。优先使用可验证的酒馆本地库；如需备用库，应随插件本地提供，不能在导入时依赖 CDN。
- 原版 1.19.0 的 Vertex 图片路径对估算超过约 2 MiB 的图片会重新编码为 JPEG；长边超过 2048 像素时会缩小，透明背景变白。不得因此另外设更低的硬上限；实际发给模型的画质要测试。
- 本地读图不需要访问 GitHub，但图片仍会随每次模型请求经过网络；Base64 会增加约三分之一的数据体积，模型联网搜索也仍需要网络。Vertex 来源可使用酒馆的网页搜索开关，但启用函数调用时 Gemini 会跳过网页搜索。自定义 OpenAI 兼容接口没有酒馆自带的网页搜索开关，能否搜索取决于中转或模型本身（尚未核实）。

## 8. 预计改动范围

| 位置 | 职责 |
| --- | --- |
| 小说生成器的角色批量运行器 | 向普通生成、重生成和预览重生成传递实际角色名 |
| 现有酒馆宿主适配与结果隔离拦截链 | 保存／读取本地图片、绑定本轮状态、向请求副本加入图片并处理停止和失败 |
| 独立图片模块 | 读取并校验本地 ZIP、缓存、角色匹配、记录用户确认 |
| 现有生成设置界面和样式 | 开关、导入入口、进度、当前图片与待确认项 |
| 现有测试及必要的新增测试 | 覆盖本地导入、名称兼容、切图、重生成、失败与旧功能回归 |

具体文件以实施前核对的最新源码为准。保留插件 ID、现有设置与 `generate_interceptor` 行为；不修改中转仓库中的图片作为实现步骤，不增加服务器插件或更换现有模型连接。

## 9. 验收：什么才算真正完成

**自动化与隔离测试**

- 使用标准 ZIP、只包含作品文件夹和图片的 ZIP、一个包含多个作品的 ZIP、中文路径、重复导入、图片损坏等样本；有问题的文件不能污染其他已导入数据。
- 验证规范化后的名称、别名、同名跨作品、缺图和歧义；不允许静默选择错误角色或沿用上一张图。
- 覆盖普通 A → B、重生成 A、候选预览、图片功能关闭、媒体内联不可用、图库及原附件保留、失败／停止／切聊天／刷新恢复；原有生成、结果隔离和导出测试继续通过。
- 检查生成、换人、失败和停止后，聊天中没有长期保存插件自动添加的图片；用户原有附件和图片库原图完整保留，重生成仍能再次取用对应原图。
- 在隔离酒馆中阻断 GitHub 访问，导入本地包后用合成模型接口检查每轮请求的图片内容与角色对应；检查的是实际图片数据，而不仅是文件名或模型自述。

**手机实测**

1. 在 SillyDroid 用手机文件选择器一次选择本地 ZIP 并导入，确认图片存入插件管理的图片库且进度正确。
2. 用两张内容明显不同的测试图完成 A → B → 重新生成 A，确认当前模型能识别对应图；条件允许时检查请求中的图片部件，不记录凭证或图片正文。
3. 测试关闭图片功能、缺图提示和停止恢复；网络可访问模型但无法访问 GitHub 时，本地图片仍应可用于生成。
4. 再验证一份约百名角色的单个作品 ZIP 在手机上的导入体验与内存；若设备无法承受，记录原因并评估低内存解析，不把桌面结果当作手机通过。

第一版完成指上述核心链路可重复通过；支持上百个角色，不限定只能处理两张图。图片内容准确性和模型联网结果仍以实际图片、来源与模型输出核对。

## 10. 后续执行顺序与边界

1. **用户审阅本蓝图。**在此之前不修改小说生成器功能。
2. 确认后先核对远程源码、手机版本和现有测试基线，再实现本地导入与名称匹配。
3. 接入每轮请求副本，覆盖正常生成和重生成，完成自动化与隔离酒馆验证。
4. 用户许可并具备设备访问能力时，在手机上验证本地选包、切图和模型请求；修正失败项后再交付。

当前已验证：仓库样本包可解压；公开 SillyTavern 1.19.0 自带 JSZip 3.10.1，在隔离 Node 环境可读取该包及中文路径。**这些都不是手机验收，也不代表导入器或送图功能已经实现。**
