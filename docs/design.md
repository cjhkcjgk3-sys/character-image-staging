# 项目方案

## 要解决的问题

用户已有「小说自动生成器」的同楼层批量写卡模式。名单按行给出完整角色名，固定提示词中的 `[[角色名]]` 随名单替换。用户希望为每一轮角色自动提供对应立绘，让同一聊天模型直接读取图片，而非依赖搜索摘要或另一个模型生成的图片描述。

## 已有依据

- 用户提供的 SillyDroid 环境：SillyTavern 1.19.0；曾验证手动图片附件可用于识图。4-argon 的白名单问题据用户反馈已处理；实际版本和发送请求仍需实机核对。
- `cjhkcjgk3-sys/Novel-Auto-Generator` 的 `3cfe67eb4099cdd0b53ddb8f36fa0c5f55616154` 版本通过角色名单替换提示词，并调用酒馆原生生成；手机实际安装版本未知。
- 参考 ST 1.19.0 公开源码，图片上传端点可写入用户图片目录，原生图片内联路径可把图片数据加入请求。是否适用于用户手机上的服务端实现仍需检查。
- 曾尝试由网页搜索获取立绘；搜索文本、图片链接、消息显示和实际模型图片输入是不同环节。现有 Web Search 桥保留为备选，不当作已经跑通的图片输入路径。

## 分工

### 1. 收集任务

输入是作品范围和角色名单，每项保留原名单全名。确认需要默认立绘还是更多外观；定位来源、获取图片、记录版本和来源。可明确匹配的结果自动处理；有歧义的结果列候选，等待用户选择。找不到或下载失败要保留原因和状态，不能借用其他角色图片。

支持分批与恢复：每批保存任务范围、完成项、待确认项和失败项；继续时先读取已有状态，避免重复收集和覆盖已有成果。是否能在对话关闭后继续由执行宿主决定。

### 2. 仓库中转

图片文件放 `images/`，清单放 `catalog/catalog.json`。以完整名单名和版本关联图片，保留来源、文件类型与哈希。原始来源受限、无法验证或不宜公开的资料应记录为待处理，不能冒充已收集。分批提交时先保证清单引用的文件在同一提交中存在。

公开仓库使他人能够读取和下载；仓库写入使用获授权的账号或 Agent。提交前检查来源的公开使用条件，不把密钥或私人数据存入仓库。

### 3. 酒馆导入与送图（待开发）

独立酒馆扩展读取仓库清单，预览差异，把图片逐批下载并导入酒馆内部图片库，保留角色到内部路径的映射。导入可重试、可恢复，显示缺失或待确认项；不要求酒馆直接访问手机外部文件夹。

每次批量写卡前，识别当前名单项并载入对应图片，图片与当前角色提示词一起进入请求。若无法唯一匹配或图片不可用，默认暂停并提示，不沿用上一位角色的图。单角色重生成同样按该角色重新选图。

仓库与导入方通过版本化清单和具体提交版本交接，避免导入中途清单变化。酒馆生成插件不必为了维护图片而改造；若独立扩展无法可靠获取当前角色，再评估一个最小的明确对接接口。

## 第一阶段范围

当前只建立公开中转仓库、数据约定与静态检查。图片收集器、酒馆扩展、自动下载、模型调用和部署均未实现。第一批实际收集应先选少量角色，覆盖明确匹配、有多个版本和失败三种情况。

## 后续验收

1. 收集：名单中每项有可追溯的结果；图片实际可读取，含待确认和失败报告。
2. 中转：仓库清单格式有效，引用的图片文件存在且哈希一致；可从中断位置继续。
3. 导入：在实际 SillyDroid 中，图片保存到酒馆用户数据，可分批重试和备份。
4. 发送：对两名不同角色及一次单角色重生成，观察请求包含相应图片，且前一角色的图片没有混入。
5. 识图：用可核对内容的图片确认当前模型直接收到并使用图片。静态检查或图片显示不能替代实际请求和识图证据。
