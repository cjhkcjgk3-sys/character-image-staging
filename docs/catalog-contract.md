# 图片清单约定（1.0.0）

`catalog/catalog.json` 是中转站和未来酒馆导入扩展之间的交接文件。它记录实际文件，不存放图片 Base64、模型生成的图片描述或账户凭据。

## 格式

根对象含 `schema_version` 和 `items`。一个条目表示一个角色的一个图片版本，完整示例见 `examples/catalog.json`。示例仅展示结构，不指向真实图片。

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定的 ASCII 条目 ID，同一条目更新时保持不变 |
| `roster_name` | 名单中的原始完整名称，保留原写法；查找时不要求所有名单使用同一种格式 |
| `work` / `character` | 作品和角色名称，方便检索和人工核对 |
| `variant` | 外观版本，如 `默认立绘` |
| `status` | `ready`、`needs_review` 或 `failed` |
| `selection` | `automatic`、`manual` 或 `unconfirmed`；不把自动筛选冒充人工确认 |
| `image_path` | `ready` 时为仓库内 `images/` 下的相对路径；其他状态可为 `null` |
| `sha256` | `ready` 时为实际文件的 SHA-256；其他状态可为 `null` |
| `mime_type` | `ready` 时为 `image/png`、`image/jpeg` 或 `image/webp` |
| `source_page` / `source_image` | 来源页面与原图片地址；未知时填 `null` |
| `note` | 待确认或失败原因；可为空 |

`ready` 表示已选定且实际图片文件可读取，不表示人工逐张确认，也不代表模型已经看过。`needs_review` 表示身份、版本或其他关键信息不明确，或仅有来源链接而未把图片文件保存到仓库；`failed` 表示本轮获取失败。对这两种状态，酒馆端不得当作可用图片。

同一 `roster_name` 可以有多个 `variant`，但同一名单名和版本的组合不能重复。第一版写卡默认使用版本名为 `默认立绘` 的 `ready` 条目；若没有或不唯一，就提示处理。后续如需为每个任务指定其他版本，应明确记录选择，不按搜索排名临时猜测。

## 未来酒馆侧的两种查找方式

这里是待实现的兼容约定，仓库本身尚无查图程序：

1. **完整名称查找**：保留用户名单原文，先用完整名称匹配 `roster_name`；可处理首尾空格、全角与半角等不改变身份的写法差异。
2. **作品和角色查找**：完整名称没有匹配时，利用条目的 `work` 与 `character` 查找；识别作品和角色的先后顺序以及常见分隔符差异。例如 `原神·温迪`、`温迪（原神）`、`原神 / 温迪` 可对应同一条 `work=原神`、`character=温迪` 的记录。用户不需要为了两种写法重复添加图片或更改原名单。

两种方式都要核对指定形象；未指定时使用唯一的默认立绘。角色别名或作品别名不能确定时提供候选，由用户选择后记住对应关系；出现多个作品、角色或版本都匹配时也应请求选择，而不是自动取第一个或沿用上一角色的图片。查不到时提示缺少图片，保留用户处理或补充的机会。

匹配应以完整作品和角色名称或明确的别名为依据，不因一个名字包含另一个名字就自动认定为同一角色。当前八条样本里的 `roster_name` 是示例，尚未与用户酒馆的实际名单核对。

## 目录和文件

- 图片路径相对于仓库根目录，如 `images/作品甲/角色甲.png`；不得使用绝对路径或 `..` 越出目录。
- 默认按作品建一层目录，图片文件名使用中文角色名；其他版本用有意义的中文版本名称区分，具体见 [图片整理方法](image-guidelines.md)。上传、URL 编码和手机文件系统差异由后续导入器处理。
- SHA-256 以文件字节计算，不因修改文件名变化。实际图片格式应与 `mime_type` 一致。
- 不同作品的同名角色要结合 `work` 或用户确认的对应关系区分。缺少作品信息时先消歧，不静默合并。
- 每次更新图片后同步更新哈希和来源；清单引用的文件应在相同仓库提交中存在。

## 校验边界

`tools/validate_catalog.py` 检查基本字段、重复项，以及 `ready` 条目的路径、文件头和可选 SHA-256。`needs_review` 候选的文件和哈希目前需要另行检查。它不联网，不证明图片身份、版本、版权状态或模型识图结果；这些需要来源核对和运行时验证。
