# 问题与解决记录

开工前先读这份记录；遇到问题就记，解决后补上解法。规则见 [开发准则](开发准则.md)「边做边记录」。三个图片仓库的这份文件内容相同，新增条目三处一起加。

**条目模板**（小问题只写现象和解法两行即可）：

```markdown
### 简短标题（YYYY-MM-DD）

- 现象：看到了什么，报错原文
- 原因：查明的原因（推断的要写明“推断”）
- 走过的弯路：试过但不行的办法（没有就省略）
- 解法：最终有效的做法，写具体命令、参数、版本
```

### 同一人只留一套本体立绘，换装算皮肤（2026-11-14）

- 现象：若把游戏里的独立换装角色（如蔚蓝档案的泳装、正月学生）也当作本体，同一个人会生成出多张角色卡。皮肤当作服装使用，不需要每人多张卡。
- 解法：每个角色只保留一套本体立绘作为初始形象。同一人的其他版本（泳装、私服、正月、圣诞、偶像、应援团、兔女郎、礼服等，即便是独立可抽角色）一律算皮肤，放进 `## 皮肤`。例外是确实不同的身份、职责或职阶（如 FGO 的 Saber / Lancer / Alter，以及律者、改造、META 等主要形态），仍分别作为本体。判断标准：同一人换了衣服 → 皮肤；不同角色条目或身份 → 独立本体。拿不准时在清单注明并先按皮肤处理。蔚蓝档案按此整理，已有换装图移到「## 皮肤」，图片不删除。其他作品只做了只读扫描，未移动。

### 皮肤立绘改为“默认不收，点名才收，要收就全收”（2026-11-14）

- 现象：原规则是挑着收写小说常用的皮肤（泳装、礼服、正月、圣诞等），每个角色一两套。这和“生成角色卡默认只用本体立绘、皮肤当作服装”的用法不一致。
- 解法：默认只收本体立绘（含改造、律者等主要形态）；只有用户明确要求给某部作品收皮肤时才收；要收就全收，不挑着收。命名仍是 `角色名（皮肤名）`，放在清单 `## 皮肤` 小节。小说生成器里皮肤默认不勾进名单，只写角色名时不会配到皮肤图。碧蓝航线已要求收皮肤，但目前「## 皮肤」小节条目为 0，按新规则应后续补全，已有图片不删除。

### GitHub Release 把中文资源名改成 default.zip（2026-11-14）

- 现象：用 `gh release create` 上传 `原神.zip` 后，Release 上的资源名变成 `default.zip`，下载地址也变成 `.../default.zip`。
- 原因：GitHub Release 不保留非 ASCII 的资源文件名，会改成 `default.zip`。ZIP 内部的中文路径不受影响。
- 解法：发布到 Releases 的文件名改用英文，例如 `原神` → `genshin.zip`、`碧蓝航线` → `azur-lane.zip`。Release 说明和 README 用对照表写出中文作品名和下载链接。ZIP 内部仍是 `原神/00-清单.md` 这种中文目录，小说生成器可以正常导入。


### 浅克隆下取图与全库检查（2026-11-14）

- 现象：用 `git clone --depth=1 --filter=blob:none --no-checkout` 后只检出清单，再用 `git checkout --ignore-skip-worktree-bits HEAD -- <图片路径>` 取图时，GitHub promisor 请求返回 503（`fatal: could not fetch <OID> from promisor remote`）；首次运行 `python3 -m unittest discover -q tests` 报多个作品的图片文件不存在。克隆后推送也曾因远端 `main` 有新提交而被 `fetch first` 拒绝。
- 原因：部分检出时工作树没有其他作品图片；仓库测试会遍历全库实际作品目录；缺失 blob 的按需 Git 请求当时返回 503。远端提交则是在克隆后更新了 `main`。
- 解法：设置 `git sparse-checkout` 后执行 `git read-tree -mu HEAD`，避免未检出的文件被误报为暂存删除。运行全库测试前，将需要检查的原图按二进制取回，写入用 `open(path, "wb")`；逐个比较 Git blob SHA-1 与 `git ls-files --stage` 中的对象 ID，确认字节完全相同后再检查。推送遇到 `fetch first` 时执行 `git fetch origin main:refs/remotes/origin/main`、`git rebase origin/main`，然后正常 `git push origin main`，不要强推。

### 混合作品中的旧名别名冲突提示（2026-11-14）

- 现象：`python3 tools/check.py images/主机与PC游戏` 显示通过，但提示 `「貂蝉」同时对应 真三国无双8貂蝉 与 真三国无双：起源貂蝉`。
- 原因：为兼容旧清单名而保留的别名带作品名；`tools/check.py` 会把 `作品别名：` 中的游戏名从别名里剥掉，两个不同游戏的旧名因此都归一成 `貂蝉`。混合作品标题已写进新文件名，两个新名本身不重名。
- 解法：保留带作品名前缀的新名和要求保留的旧全名别名；核对完整清单中的正式名和链接后，记录这是检查器的别名冲突提示（该命令退出码为 0），不要为消除提示删除必需别名或作品前缀。


### 图片经文本通道传输后被截断（2026-11-13）

- 现象：碧蓝航线 887 张里 624 张打不开，大小全在 786,441–786,444 字节；其中 179 张 PNG 结尾还带着完整的 IEND，只看结尾查不出。
- 原因（推断）：图片经 base64 文本通过了一个约 1 MB 上限的通道（聊天、工具调用或 GitHub 内容接口），768 KB 二进制转 base64 正好约 1 MB，超出部分被丢掉。
- 解法：图片一律按二进制下载写盘（`open(p, "wb")`），用 `git add` + `git push` 提交（凭据由 gh 或 git 凭据助手提供，不写进仓库）；保存后用 Pillow `Image.open(p).load()` 完整解码。不要用 GitHub 内容接口或 base64 写图片。

### defect_check.py 把每张图都报成读取失败（2026-11-13）

- 现象：所有图片都被标“读取失败”。
- 原因：OpenCV 5.0.0.93 没有 `cv2.CascadeClassifier` 顶层接口。
- 解法：`pip install opencv-python-headless==4.11.0.86`。

### 重新下载修不好残图（2026-11-13）

- 解法：直接换图源，用 BWIKI 对应角色的完整立绘；BWIKI 立绘只有 350×525 时用同形态官方海报。

### GitHub raw 返回 404（2026-11-13）

- 现象：数据里写的 `z13_rw.webp` 请求 404。
- 原因：raw 路径区分大小写，实际是 `Z13_rw.webp`。
- 解法：先拉一次目录树（`git/trees/main?recursive=1`）存到本地，按树里的真实路径下载。

### 战双帕弥什官方 CDN 握手超时与中文 URL 异常（2026-11-14）

- 现象：访问库洛官网静态资源 `https://media-cdn-zspms.kurogame.com/...` 时频繁报 `urllib.error.URLError: <urlopen error _ssl.c:1011: The handshake operation timed out>`；且部分含有中文字符或空格的宣传图直链报 `InvalidURL` 或 `ascii codec` 编码错误。
- 原因：该 CDN 的某些 Tengine 节点在特定 Python OpenSSL 客户端握手时延迟较大导致超时；Python 标准库 `urllib.request` 对未 URL 编码的非 ASCII 路径直接拒绝。
- 走过的弯路：反复使用 HTTPS 短超时重试导致批处理被卡在握手阶段。
- 解法：
  1. 将图源 URL 协议切为明文 `http://media-cdn-zspms.kurogame.com/...` 并设置 20s 超时配合多线程重试，下载速度极快且完全无 SSL 握手延迟。
  2. 使用 `urllib.parse.quote(path)` 对 URL 路径中的中文字符和空格做标准转义后请求。

### Windows Python 缺少系统时区导致测试报错（2026-11-14）

- 现象：运行单元测试 `python -m unittest discover tests` 报 `zoneinfo._common.ZoneInfoNotFoundError: 'No time zone found with key Asia/Singapore'`，导致 `test_publish_work_zips` 失败。
- 原因：Windows 系统原生不自带 IANA tzdata 数据库，Python 3.9+ 的 `zoneinfo` 在 Windows 下依赖第三方 `tzdata` 包。
- 解法：在 Python 环境中执行 `pip install tzdata` 即可解决全量单元测试时区解析依赖。

### 皮肤涂装立绘全量收集策略与多源匹配（2026-11-14）

- 现象：官网 `MainMenu.json` 仅包含 6 张最近宣发的新涂装海报，而游戏内已实装涂装超过 150 款；用户明确要求落实“要收就全收”。
- 原因：游戏官网静态数据只沉淀当期版本宣发物料，历史与常规涂装沉淀在玩家社区维基（BWIKI 与 GrayRavens / Miraheze）。
- 解法：
  1. 爬取 BWIKI「涂装图鉴」全量 193 款词条，解析所属机体、角色与原图直链。通过前缀过滤与清单 65 名角色（35 组根角色名）进行机体归属匹配，筛选出清单女角色与联动角色的全部 148 款实装涂装。
  2. BWIKI 单个涂装页面通常同时存在 128x128 图标、256x512 橱窗卡牌与 2000x3240 / 4000x6480 透明立绘原图；通过下载候选图片比较分辨率面积（`width * height`）自动精准识别并提取出全身透明立绘。
  3. 针对尼尔联动角色（2B、A2），从 Miraheze 抓取《尼尔：人工生命》与《尼尔：自动人形》经典限定涂装「2B（凯妮的服装）」与「A2（破坏者装束）」的高清透明立绘。
  4. 最终收录 156 款官方实装涂装，涵盖全量清单角色。

### Windows Python 下载特定 CDN 节点超时与 curl.exe 调度（2026-11-14）

- 现象：Python `urllib` / `requests` 直连部分图片源（如 `patchwiki.biligame.com`）时偶发 `WinError 10060` 连接超时，而同机执行 Windows 自带 `curl.exe` 下载极速且 100% 稳定。
- 原因：Windows 下 Python 默认会读取 WinINet 代理配置或解析到系统 TUN/虚拟网段 fake-IP（`198.18.0.x`），若底层 raw socket 握手受阻会导致超时。
- 解法：在 Python 批处理脚本中通过 `subprocess.run(['curl.exe', '-s', '-A', 'Mozilla/5.0', '--compressed', ...])` 调度系统原生网络协议栈，结合 `ThreadPoolExecutor(max_workers=8)`，150 张超大原图在 30 秒内全部完成下载与转码。

### Windows 文件系统 Pillow 惰性加载导致句柄占用（WinError 32）（2026-11-14）

- 现象：`Image.open(tmp_path)` 打开临时图片后直接 `tmp_path.unlink()` 时，报 `PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问`。
- 原因：Pillow 的 `Image.open()` 是惰性读取文件，在 Windows 文件系统下会持续独占锁定句柄，未显式关闭前无法删除。
- 解法：统一采用 `with Image.open(tmp_path) as im: best_im = im.copy()`，确保离开上下文时底层文件句柄立刻关闭释放，再安全调用 `unlink()`。

### 警惕官网 PC 背景 Banner（16:9 裁剪图）误当立绘，须使用涂装图鉴提取纯透明全身立绘（2026-11-14）

- 现象：自检排查发现战双帕弥什 65 名本体机体立绘及部分前期皮肤均为 1920×1080 横版半身图（如用户指出的露西亚·誓焰、维罗妮卡·铮骨等截断在腰部）；个别涂装误收了 380×654 橱窗卡牌。
- 原因：
  1. 早期从库洛官网 `MainMenu.json` 的 `pictureType == 15`（PC 官网 16:9 横版背景 Banner）提取，该类资源是官方前端为宽屏页面设计的半身横向物料，腰部以下被全部裁切。
  2. 前期添加的 6 张皮肤海报中，「含英（拂晓晴岚）」实际是 2024.05 版本宣发插画而非涂装，其对应的真实涂装「泠泫旖碧」已在库中收录。
  3. 部分 BWIKI 页面中包含 380×654 橱窗预览卡牌，早期按大小选择时未覆盖多图候选。
- 解法：
  1. 角色本体全身图源切换：通过 GrayRavens (Miraheze) Wiki 的 MediaWiki API 获取各机体初始形态 `Coating-<FrameCode>-Generic.png`（如 `Coating-Pyroath-Generic.png`、`Coating-Aegis-Generic.png`、`Coating-Lotus-Generic.png` 等），100% 精确映射 65 名角色本体的真实高清纯透明全身立绘（高度 1600~3300px）。
  2. 横版皮肤图源切换：针对前期横版皮肤海报（比安卡·残梦道标、露西亚·汲刃成棘、卡列尼娜·幻日旅轮、亚里莎·薄暮礼赞、露娜·弥月潜行），在 Miraheze 抓取对应涂装的 3000px 高清透明全身立绘（如 `Coating-Abystigma-Alt1.png`、`Coating-CrimsonWeave-Alt6.png` 等）。
  3. 清理非皮肤插画：删除冗余的宣发插画「含英（拂晓晴岚）.webp」并在 `00-清单.md` 中移除对应条目。
  4. 缩略图卡牌升级：针对丽芙·莲歌行、斜奏·纤卉裁风、涅缇娅·幽林巫祷、含英·鸿韵绣春、比安卡·春围巡狩，重新抓取 2048px/1800px 透明全身立绘。
  5. 自动化压制与验证：采用系统原生 `curl.exe` 并发下载，Pillow `getbbox()` 自动裁切多余透明边缘，动态调节质量压制至 `< 1,000,000 字节`。全库 220 张立绘长宽比自检全部通过（0 张横版，0 张非透明），`tools/check.py` 与单元测试全绿通过。
