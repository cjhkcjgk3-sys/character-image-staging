## 二、图片标准（硬性）

1. **单图严格小于 1,000,000 字节，不设最低体积。** 不为凑体积放大图片，也不因图片小于 500 KB 拒收。体积只是仓库上限，不是清晰度指标。
2. **清晰、全身、可辨认。** 人物不糊，眼睛颜色和瞳孔花纹能看清，脸部和服装细节清楚；优先全身立绘，半身、大头和只剩舰装／场景的图不收。
3. **人物本体完整。** 头（含头发、耳朵、头顶光环）、脸、躯干、手臂、手、腿、脚、服装都要在图内。伸出本体的武器、技能特效、随从和大场景可以裁掉。
4. **画面完整。** 能解码不等于画面完整：透明缺口、矩形切口、横向拖影、碎片拼接、缺脸、选错图层都算残图。
5. **优先官方或 Wiki 原图**（BWIKI、萌娘百科、Fandom、官网等），不用 AI 生成图和 Pinterest 图；有文字或背景可以接受，只要角色本身清楚。

## 三、处理流程

1. 读 `README.md`、本文和目标作品的 `00-清单.md`。
2. 找稳定图源，先拿 3 到 5 个角色试跑完整流程，再分批下载。
3. **按二进制下载和写盘**（`open(path, "wb")`），用 `git add`/`git push` 提交。不要把图片转成 base64 文本经过聊天、工具调用或 GitHub 内容接口写入（约 1 MB 上限会把图悄悄截断）；不要用 PowerShell 的 `>` 重定向保存图片。
4. 每张图用 Pillow 完整解码一次（`Image.open(p).load()`）。
5. 已小于上限且构图合适的图原样使用；超限图按第四节**按需裁剪，再压缩**。
6. 复核构图（第六节工具），确认眼睛、脸部和服装仍可辨认后，在清单勾选并链接。
7. 提交前跑 `python3 tools/check.py images/<作品>`（CI 也会跑）。
8. 如实汇报：收了多少、剩多少、遇到什么问题、怎么解决；新坑补进本文第八节。

## 四、按需裁剪与压缩（先裁后压，但只在需要时裁）

裁剪不是固定前置步骤。先分别看像素长边、文件体积、人物完整度和留白；像素大不等于文件超限，文件小也不等于需要裁。需要裁时，一律先裁再压缩。

- **已合规的图不动**：已小于 1,000,000 字节且构图合适的图，无论像素多大都不因体积规则而裁；若大片留白让人物明显太小，可在人工确认后为构图裁剪。
- **超限小图全画幅编码**：长边不超过约 2,000 像素的超限图，直接对完整画面高质量编码，不因尺寸小而裁掉人物或细节。
- **超限大图只在有收益时裁**：全画幅能以 WebP 质量 90 及以上低于上限时直接全画幅编码；只有全画幅需要降到质量 90 以下、且安全去除留白能保住清晰度时才裁。没有可安全去掉的空白时保留完整画幅，直接缩放或编码。
- **居中与完整优先**：裁框以人物本体中心为中心，能留边时留约 3%–5%；空间不足就缩小边距，不得把人物挤偏或切掉部位。做不到既完整又居中就放弃裁剪。禁止放大。裁剪补不回源图本身缺失的部位。
- **压缩**：WebP `method=6`，从质量 98 开始逐档下调，首次低于上限即停；有透明通道的保留透明通道。质量低于 90 的结果必须对照原图目视复核眼睛和脸部；降到 80 仍超限时换更合适的源图，不要继续盲目降质。
- **带背景的图不能全自动裁**：工具看不准的会标成 `manual`，不会自动改写，必须先看预览联系表。

```bash
python3 tools/crop_character.py images/<作品>                    # 只读：生成裁框预览和 JSON（out/crop_preview/）
python3 tools/crop_character.py images/<作品> --apply              # 只处理超限图：优先全画幅编码，必要时才裁
python3 tools/crop_character.py images/<作品> --apply --force-crop # 看过预览、确需改善构图时，允许裁已合规图（仅 auto 项）
```

预览为品红底，左侧红框是建议裁剪范围，右侧是裁后效果。检测结果不能代替目视确认；预览显示人物偏移或任何部位可能被切掉时不要应用。

## 五、清单与命名

清单 `images/<作品>/00-清单.md` 是唯一数据源。小说自动生成器（1.15 起）导入作品 ZIP 时会读出清单里**全部**角色名（含未勾选项），用户可以一键加入角色名单，名字按清单原样使用。所以清单里的名字就是最终写进小说的名字，必须写准。

**命名模型：作品名（前缀，可选）＋ 角色名 ＋（立绘名）。** 文件名写成 `角色名（立绘名）`，作品名省略，因为作品文件夹已经表示作品。

| 部分 | 写法 | 说明 |
|---|---|---|
| 作品名（前缀） | `崩坏三`、`碧蓝`、`最终幻想7` | 普通作品的文件名和清单不写；小说角色名单里写不写都行，两种都能匹配。混合作品文件夹例外，见下。作品名要出现在清单标题或 `作品别名：` 里，插件才认得出、去得掉。 |
| 角色名 | `亚瑟`，不写 `亚瑟·潘德拉贡` | 取最常见的简短名。同一文件夹里不得重名：简称会和别的角色撞名时（如绝区零 `安比` 与 `零号·安比`），保留能区分的写法。 |
| 立绘名（后缀） | `（亡灵骑士）`、`（改造）`、`（雷之律者）` | 永远只写这张立绘的形态、装甲或皮肤名，写在全角括号里，不写作品名或游戏名；本体立绘不写后缀。 |

例子：`亚瑟（亡灵骑士）`；`拉菲`、`拉菲（改造）`；崩坏3 文件夹里的 `雷电芽衣（雷之律者）`、`雷电芽衣（始源之律者）`。小说角色名单里写 `崩坏三雷电芽衣（雷之律者）`、`雷电芽衣雷之律者` 也能对上同一张图。

**混合作品文件夹（如 `主机与PC游戏`）不拆分**，一个文件夹里放多款游戏。这里文件名要带作品名前缀：`作品名角色名（立绘名）`，例如 `最终幻想7蒂法`、`最终幻想7蒂法（女仆装）`。括号里仍然只写立绘名，不写游戏名。每个用到的游戏名都要写进该清单的 `作品别名：`，否则名单写 `蒂法（女仆装）` 会对不上。名单写 `蒂法（女仆装）`、`最终幻想7蒂法（女仆装）` 都能匹配；两个游戏都有 `蒂法` 时，只写 `蒂法` 会因多候选而不用图，要写上作品名。名单写成别的游戏名（如 `最终幻想8蒂法`）时不会配到 `最终幻想7蒂法` 的图（小说生成器 1.15.2 起），显示无图。

**同一作品里，每个形态只用一种固定的后缀写法**：统一写 `改造`，就不要有时写 `改`。插件对后缀逐字比较（只忽略括号样式、标点和空格），`拉菲改` 对不上 `拉菲（改造）`。最省事的做法是在小说生成器里用“📋 从清单添加到名单”，名字原样复制自清单，和图片名天然一致；手写名单时照抄清单写法。这套规则的目的是尽量减少对不上的情况，不追求覆盖所有写法。

- 标题保持 `# <作品名>角色图片清单`；作品简称写在开头的 `作品别名：` 行。生成器从标题、作品别名和文件夹名识别作品名。
- 勾选格式 `- [x] [角色名](角色名.webp)`；未收到图保持 `- [ ] 角色名`，不用占位图凑数。文件名有空格或半角括号时写成 `[名字](<文件名.ext>)`。
- **链接文字与文件名（不含扩展名）必须逐字相同**，都用简体中文角色名；临时编号只用于核对来源，不做文件名。
- 同一角色若有不同身份、职阶，或作为主要身份的形态（如 `三月七（巡猎）`、`拉菲（改造）`），各占一行，后缀用全角括号写在名字里，不要写在链接外面。这些属于本体立绘。同一人的换装或活动版本不是本体，写法见下面的「皮肤立绘收录规则」。
- 其他称呼写在行尾 `别名：`；未勾选项可写 `备注：待重找的原因`，它不算名字。不要擅自改动已有角色名和别名，需要修正时单独说明。
- 皮肤的收录范围、命名和清单写法见下面的「皮肤立绘收录规则」。

### 皮肤立绘收录规则

小说生成器生成角色卡时默认只用本体立绘。皮肤当作服装：可以做成服装卡，或作为素材资料保存。因此收集时也按这个用法来。

- **每个角色只保留一套本体立绘，作为初始形象。** 目的是避免同一个人生成出多张角色卡。
- **同一人的其他版本一律算皮肤**，放进清单的 `## 皮肤` 小节。包括换装和活动版本，例如泳装、私服、正月、圣诞、偶像、应援团、兔女郎、礼服，即便游戏把它们做成独立可抽角色，也按皮肤处理。
- **例外：确实是另一个角色条目时，仍分别作为本体。** 判断标准是：只是同一人换了衣服，就算皮肤；是不同的身份、职责或职阶，才算独立本体。例如 FGO 里同一英灵的不同职阶（阿尔托莉雅的 Saber、Lancer、Alter）保留为各自的本体，因为每个职阶实际上是独立角色。剧情里作为主要身份的形态（律者、改造、META、μ兵装、巡猎等）也留在本体。拿不准时在清单里注明，并先按皮肤处理。
- **蔚蓝档案是这一条的典型例子：** 泳装、私服、正月、应援团、兔女郎、偶像等版本都是皮肤，不是独立角色。每位学生只留一套初始本体立绘；已收到的换装已移到「## 皮肤」。用户尚未点名要为这部作品收皮肤，已有图片一律保留，也不再额外补收。
- **默认只收本体立绘。** 没有另外说明时，不要收皮肤。
- **只有用户明确要求给某部作品收皮肤时才收。** 没有点名的作品不收皮肤。
- **要收就全收，不挑着收。** 一旦某部作品要收皮肤，就把该作品的皮肤立绘全部收齐。要么不收集，要么全收集。
- **命名与清单：** 命名写成 `角色名（皮肤名）`，如 `拉菲（泳装）`；放在清单单独的 `## 皮肤` 小节，和本体分开勾选；图片标准与本体相同。
- **插件里的用法：** 从清单添加到名单时，皮肤在单独的折叠分组里，默认不勾选。名单只写 `拉菲` 时只用本体图，不会配到皮肤图；只有写 `拉菲（泳装）` 才会用对应皮肤。

碧蓝航线已要求收集皮肤。按这条规则，清单的「## 皮肤」小节最终应收全；目前这一节仍是部分收录（现有皮肤条目 0 条），已有图片一律保留，后续再补全。

**生成器的名字匹配规则（以 Novel-Auto-Generator 1.14 起的实现为准）**：名单名 =［作品名，可选，可在前缀或括号里］+ 角色名 +［后缀（备注）：皮肤／装甲／形态，可选］。按顺序比较：① 完整名称；② 去掉作品名后的“角色名＋备注”；③ 没有备注时只比角色名（含别名）。比较时只忽略全／半角、括号、标点、空格和间隔号，例如 `安比（绝区零）改`、`绝区零安比改`、`安比改` 都对应 `安比（改）`。写了备注但没有对应形态图时按无图处理，不拿本体图顶替；不做包含或模糊匹配（`小安比` 不会匹配 `安比`）；同层多张候选时不用图并提示原因。因此后缀写法要和图片名逐字一致：图片叫 `拉菲（改造）`，名单写 `拉菲改` 就对不上。只有形态图、没有本体图时，名单只写 `雷电芽衣` 也是无图，要写出后缀。`tools/check.py` 里的 `match_name` 带包含匹配，只用于 CI 的别名冲突提示，不代表生成器的行为。

## 六、复核与检查工具

批量图验收分两关：**字节完整**（解码、CRC、体积）和**画面完整**（错图、缺头缺脸、透明缺口、主体太小）。第二关只能靠看图。

| 工具 | 作用 |
|---|---|
| `python3 tools/check.py images/<作品>` | 已勾选项的路径、格式与文件头、结构完整性（PNG 逐块 CRC、WebP 声明长度、JPG 结束标记）、小于 1,000,000 字节；别名冲突警告。不取代 Pillow 完整解码。 |
| `python3 tools/audit_framing.py images/<作品>` | 为清单内**全部**已勾选图（旧图新图都算）生成分页 HTML 缩略图图库（`.image-audit/`，默认每页 48 张）和洋红底编号联系表；橙框只是提示。 |
| `python3 tools/defect_check.py <作品> --sheet --all-levels` | 自动预筛残图，结果在 `out/defect_check/`：“高”（直线裁切／矩形空洞）基本是真残图；“低”（无人物／找不到脸）误报多。只读，是否取消勾选由人决定。依赖 Pillow、numpy、`opencv-python-headless==4.11.0.86`（OpenCV 5 缺 `cv2.CascadeClassifier`，会把每张图误报为读取失败）。 |
| `python3 tools/crop_character.py` | 见第四节。 |
| `python3 -m unittest discover -q tests` | 改工具后跑全部测试。 |
| 自动打包（CI） | 每次 `images/` 更新后，GitHub Actions 把每个有图的作品打成 ZIP，发布到该仓库 Releases 的「图片下载」页（`tools/publish_work_zips.py`）。 |

规则：图库或联系表“已生成”不等于“已复核”，要实际逐页扫完并记录扫过的页数；视觉模型、人脸检测只给候选，不能自动放行或判错；被标记的图点开原图，与可信来源或同角色其他立绘比对后再决定。`out/`、`.image-audit/` 已在 `.gitignore`，不要提交。

## 八、已踩过的坑

- **base64 截断（碧蓝航线）**：887 张里 624 张打不开，大小都在 786,441–786,444 字节（≈768 KB，转 base64 正好约 1 MB）；其中 179 张 PNG 结尾的 IEND 还被补过，只看结尾查不出。→ 二进制下载、git 推送、完整解码。
- **源图本身就是残图**：多张碧蓝缺脸、碎片、只剩舰装或舞台的图与上游客户端拆包资源逐字节相同，重复下载修不好。→ 改用 BWIKI 对应角色的完整立绘；BWIKI 立绘只有 350×525 时用同形态官方海报。
- **能解码 ≠ 构图完整**：贝奇旧图 Pillow 解码、仓库检查都通过，但头脸不在图内。旧图也必须和新图一起做全量缩略图复核。
- **按 ID 对图，不按名字猜**：碧蓝 887 项里 72 项与数据源中文名不一致（旧译名、舰名代码、`μ兵装` 括号差异）。先用 ID 映射找图，再保存为清单里的简体中文名。明日方舟按简中 `character_table.json` 精确映射角色 ID。
- **GitHub raw 路径区分大小写**（`z13_rw.webp` 实际是 `Z13_rw.webp`）；GitHub 内容接口只内嵌 1 MB 以下文件，大文件走 raw 也容易断，能走 Wiki/CDN 就别走 GitHub 接口。
- **BWIKI 直链**：`https://wiki.biligame.com/<站>/api.php?action=query&titles=File:<角色名>立绘.png&prop=imageinfo&iiprop=url&format=json` 取 `patchwiki.biligame.com` 直链；查询过多会返回 HTTP 567，知道文件名后可用 `Special:Redirect/file/<文件名>`（带浏览器 User-Agent 和角色页 Referer）。先缓存文件名、直链和目录树再下载。
- **并发 2～3 个、请求间隔约 1 秒、失败重试**，不留半截文件。站点可用性只是当次观察（如 Fandom 曾返回 402），换环境先抽样测试。
- **Wiki 角色列表可能过期**：绝区零 BWIKI 图鉴停在 2026-09-22，少列 3.3 新角色，名单要和版本公告交叉核对。
- **Windows 国内网络克隆失败**：`git config --global http.sslBackend schannel`，克隆加 `--filter=blob:none`。
- **不要为通过检查改数据**：不修改文件结尾、不伪造标记、不用占位图；汇报以验证通过的数量为准。
