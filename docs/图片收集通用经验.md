# 图片收集通用经验（给所有 AI 协作者）

这份文档汇总了原神（Gemini 完成）和碧蓝航线（GPT 完成）两次批量收图的经验和教训。开始给任何作品收图之前先读一遍，可以少走很多弯路。原神那次更细的过程见[原神填补经验参考](原神填补经验参考.md)。

## 一、必须做到的事

1. **每张图都要真正打开验证。** 只看文件头和大小不够。碧蓝航线有 624 张图文件头正确、大小也合规，但其实打不开。保存后用 Pillow 完整解码一次（见第四节的脚本），打不开就不要勾选。
2. **图片字节始终按二进制处理。** 下载后用 `open(path, "wb")` 直接写盘，提交用 `git add` 和 `git push`。不要把图片转成 base64 文本再经过聊天、工具调用或 GitHub 内容接口写入仓库，这条通道通常有约 1MB 的上限，会把图悄悄截断。
3. **不要用 Shell 重定向保存图片。** PowerShell 的 `>` 会按文本重新编码，把图片字节转坏。
4. **只设 1,000,000 字节的严格上限，不设最低体积。** 清晰度优先；文件大小不能代替画面检查。不要为凑体积放大图片，也不要因图片小于 500 KB 就拒收。
5. **提交前检查图像和清单。** `python3 tools/check.py images/<作品>` 会检查已勾选项的路径、格式、结构完整性和小于 1,000,000 字节上限；批量收集还要用 Pillow 完整解码每张图。check.py 的结构检查包括 PNG 逐块 CRC、WebP 声明长度和 JPG 结束标记，但不取代完整解码。
6. **如实汇报。** 汇报数量时以验证通过的为准，没有收全就照实说剩多少。不要为了让检查通过而修改文件结尾或伪造标记。

## 二、碧蓝航线的教训：图片被截断

**现象。** 887 张里有 624 张打不开。这些坏图的大小全都落在 786,441 到 786,444 字节之间，也就是约 768KB；而好图没有一张比这个大。

**原因（根据文件推断）。** 768KB 的二进制换成 base64 文本正好约 1MB。图片应该是以文本形式经过了一个只收得下约 1MB 的环节，超过的部分被直接丢掉了。其中 179 张 PNG 的结尾却带着完整的结束标记（IEND），中间数据是坏的，说明截断后结尾被补过，只看结尾也发现不了。

**怎么避免。** 按第一节第 1、2 条做：二进制下载、二进制写盘、git 推送，保存后完整解码验证。已确认的上游恢复源与映射方式见下节。

**恢复记录（2026-11-13）。** 从配套舰船数据按 ID 映射恢复了缺失的 624 张，原有 263 张保留原字节并改为简体中文角色名；最终 887 张全部通过 Pillow 完整解码及小于 1 MB 检查，清单中 8 个新增条目仍缺图。623 张取自上游客户端立绘仓库；Z13 的默认透明图存在大小写路径问题且画面有缺块，改用 BWIKI 的完整初始立绘。

## 三、原神的经验：稳定拿到完整原图

1. **优先用官方或 Wiki 的图片直链。** 原神的立绘可以通过 BWIKI 的 MediaWiki 接口查到直链，再从 `patchwiki.biligame.com` 的国内 CDN 下载，又快又稳：
   `https://wiki.biligame.com/ys/api.php?action=query&titles=File:<角色名>立绘.png&prop=imageinfo&iiprop=url&format=json`
   碧蓝航线这次的恢复源是 [AzurLane-AssetDownloader 提取的立绘仓库](https://github.com/iujab/azurlane-images)及其配套的 [Lycoris-AzurAPI 舰船数据](https://github.com/iujab/Lycoris-AzurAPI)。数据文件将舰船 ID、简体中文名和默认立绘直链对应起来；旧清单 887 个 ID 均能映射，抽查的 3 张现存图与上游图解码后像素完全相同，5 张待恢复样本也通过下载与完整解码。恢复时用 ID 仅作临时映射，仓库文件名统一使用简体中文角色名。其他作品同理：萌娘百科、BWIKI 对应的游戏站、Fandom（可加 `format=original` 获取原图）、官网和官方社交账号。不要用 AI 图和 Pinterest。
2. **从 GitHub 拉大文件要小心。** GitHub 内容接口返回 JSON 时只内嵌 1MB 以下的文件；大文件要用 raw 方式，且容易中途断开。能走 Wiki 或 CDN 就别走 GitHub 接口。
3. **控制并发。** 同时开太多请求会被限流或断连。2 到 3 个并发、请求之间停 1 秒比较稳。下载失败就重试，不要把半截文件留下。
4. **先缓存索引。** 需要从某个仓库挑文件时，先一次拉下整棵目录树存到本地，再按需下载，避免反复查询。
5. **网络不稳时的 git 设置（Windows 国内网络）。** `git config --global http.sslBackend schannel`，克隆时加 `--filter=blob:none`。

## 四、调整大小和验证（可直接用）

```python
from pathlib import Path
from PIL import Image

MAX_EXCLUSIVE = 1_000_000

def verify(path: Path) -> bool:
    try:
        with Image.open(path) as im:
            im.load()  # 完整解码，截断或损坏会在这里报错
        return path.stat().st_size < MAX_EXCLUSIVE
    except Exception:
        return False

def fit(src: Path, dst_stem: Path) -> Path:
    """保持清晰度并确保最终文件小于 1 MB；不设最低体积。"""
    im = Image.open(src)
    im.load()
    if src.stat().st_size < MAX_EXCLUSIVE:
        return src
    has_alpha = im.mode in ("RGBA", "LA", "P")
    out = dst_stem.with_suffix(".webp")
    img = im if has_alpha else im.convert("RGB")
    for q in (98, 96, 94, 92, 90):
        img.save(out, format="WEBP", quality=q, method=6, exact=True)
        size = out.stat().st_size
        if size < MAX_EXCLUSIVE:
            break
    if size >= MAX_EXCLUSIVE:
        raise ValueError(f"高质量重新编码后仍超出 1 MB，需要找更合适的源图或评估安全裁切：{src}")
    assert verify(out), f"验证失败：{out}"
    return out
```

## 五、清单约定（容易写错的地方）

- 勾选格式是 `- [x] [角色名](文件名.ext)`；文件名带空格或括号时用尖括号 `[角色名](<文件名.ext>)`。
- 同一角色的不同版本是清单里单独的一行，名字写成 `三月七（巡猎）`（全角括号在链接文字里面），不要把版本写在链接外面。
- 不要改动清单里的角色名和「别名：」。名字需要修正时单独说明。
- 文件名使用简体中文角色名，便于人工检索和与任务清单比对；编号只用于临时核对来源，不作为最终文件名。
- 没收到图的角色保持 `- [ ]`，不要用占位图凑数。

## 六、建议的工作流程

1. 读 `README.md`、本文档和目标作品的 `00-清单.md`。
2. 找到稳定的图源，先拿 3 到 5 个角色试跑：下载、调整大小、完整解码验证。
3. 分批下载；每张先完成二进制写盘、完整解码和人物清晰度检查，再勾选。不要因为分批而把未验证图片标为已收集。
4. 提交前跑 `tools/check.py`，并对本次图片做 Pillow 完整解码。
5. 汇报时写清楚：收了多少、剩多少、遇到什么问题、怎么解决的。有新的坑，补充到这份文档里。

## 七、原图库（谷歌云端硬盘）与仓库的分工

原图和仓库里的工作图分开存放：

- **原图库**：谷歌云端硬盘里的「角色原图库」文件夹（账号 cjhkcjgk3@gmail.com），[打开文件夹](https://drive.google.com/drive/folders/1ulEfyYerSIFJ3rTJKB-29Qb24YAG_7mh)。里面每部作品一个子文件夹，名字和仓库 `images/` 下的文件夹完全相同。
- **仓库**：存压缩后的工作图和清单，供角色卡和 AI 当参考图使用。

### 收集原图的人（GPT、Gemini 等）要做的

1. 把原图放进对应作品的子文件夹，**不压缩、不改尺寸、不转格式**，保持来源的原样。
2. 文件名就用清单里的角色名，例如 `温迪.png`、`三月七（巡猎）.png`，扩展名保持原图的格式。
3. 上传前先用 Pillow 完整打开一次，确认图片完整（第一节第 1 条）。用连接器上传时尤其要小心，大文件经过 base64 文本可能被截断，上传后对比一下云盘上显示的大小和本地文件大小。
4. 原图没有大小上限，越清晰越好；人物太小或太糊的不要。
5. 不要改动仓库里的清单勾选状态，勾选由压缩环节负责。

### 压缩环节要做的

从原图库取图，压成长边约 1600 到 2000 像素的高质量图片（有透明背景的用 WebP），验证能打开后放进仓库对应文件夹，在清单里勾选并写好链接，跑检查后提交。原图库里没有、但仓库里已有的图保持不动。
