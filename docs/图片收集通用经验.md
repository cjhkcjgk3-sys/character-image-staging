# 图片收集通用经验（给所有 AI 协作者）

这份文档汇总了原神（Gemini 完成）、碧蓝航线（GPT 完成）和星穹铁道（GPT 完成）三次批量收图的经验和教训。开始给任何作品收图之前先读一遍，可以少走很多弯路。原神那次更细的过程见[原神填补经验参考](原神填补经验参考.md)。

## 一、必须做到的事

1. **每张图都要真正打开并看构图。** 只看文件头和大小不够。碧蓝航线有 624 张图文件头正确、大小也合规，但其实打不开。保存后用 Pillow 完整解码一次（见第四节的脚本）；再确认人物头脸、关键服饰和主体没有被画框裁掉。文件能解码只证明字节完整，不证明画面构图完整。复核必须覆盖清单中全部已勾选图片，包括以前保留的旧图；用 `python3 tools/audit_framing.py images/<作品>` 生成分批缩略图图库，逐页总览，疑似有问题时再点开原图。
2. **图片字节始终按二进制处理。** 下载后用 `open(path, "wb")` 直接写盘，提交用 `git add` 和 `git push`。不要把图片转成 base64 文本再经过聊天、工具调用或 GitHub 内容接口写入仓库，这条通道通常有约 1MB 的上限，会把图悄悄截断。
3. **不要用 Shell 重定向保存图片。** PowerShell 的 `>` 会按文本重新编码，把图片字节转坏。
4. **只设 1,000,000 字节的严格上限，不设最低体积。** 清晰度优先；文件大小不能代替画面检查。超限时先按第九节裁剪（人物本体必须完整，武器和特效可裁），再压缩；不要为凑体积放大图片，也不要因图片小于 500 KB 就拒收。
5. **提交前检查图像和清单。** `python3 tools/check.py images/<作品>` 会检查已勾选项的路径、格式、结构完整性和小于 1,000,000 字节上限；批量收集还要用 Pillow 完整解码每张图。check.py 的结构检查包括 PNG 逐块 CRC、WebP 声明长度和 JPG 结束标记，但不取代完整解码。
6. **如实汇报。** 汇报数量时以验证通过的为准，没有收全就照实说剩多少。不要为了让检查通过而修改文件结尾或伪造标记。

## 二、碧蓝航线的教训：图片被截断

**现象。** 887 张里有 624 张打不开。这些坏图的大小全都落在 786,441 到 786,444 字节之间，也就是约 768KB；而好图没有一张比这个大。

**原因（根据文件推断）。** 768KB 的二进制换成 base64 文本正好约 1MB。图片应该是以文本形式经过了一个只收得下约 1MB 的环节，超过的部分被直接丢掉了。其中 179 张 PNG 的结尾却带着完整的结束标记（IEND），中间数据是坏的，说明截断后结尾被补过，只看结尾也发现不了。

**怎么避免。** 按第一节第 1、2 条做：二进制下载、二进制写盘、git 推送，保存后完整解码验证。已确认的上游恢复源与映射方式见下节。

**恢复记录（2026-11-13）。** 从配套舰船数据按 ID 映射恢复了缺失的 624 张，原有 263 张保留原字节并改为简体中文角色名；最终 887 张全部通过 Pillow 完整解码及小于 1 MB 检查，清单中 8 个新增条目仍缺图。623 张取自上游客户端立绘仓库；Z13 的默认透明图存在大小写路径问题且画面有缺块，改用 BWIKI 的完整初始立绘。

### 本次恢复的排错顺序

1. **先按旧清单 ID 对图，不按 API 中文名猜。** 887 项中有 72 项与数据里的 `names.cn` 不一致或没有中文名，包含旧译名、舰名代码和 `μ兵装` 括号差异。用旧 ID 找到图后保留清单中的简体中文名作为文件名，避免名字近似造成错配。
2. **GitHub raw 路径区分大小写。** Z13 的 API 写成 `z13_rw.webp`，直接请求返回 404；查看上游仓库 tree 后发现实际路径是 `Z13_rw.webp`。不过该透明图虽然能被 Pillow 解码，和背景合成后仍能看到大块缺失区域，因此没有勾选使用，改从 BWIKI 的 `文件:Z13立绘.jpg` 获取完整原图（853,261 字节，1000×1500）。遇到透明图时将它合成到白色或灰色背景并看缩略图；“能解码”不等于“画面完整”。
3. **图源次序按实际可用性切换。** 这次 623 张从客户端立绘仓库 raw 链接下载，使用 3 个并发并对失败请求重试；Z13 用 BWIKI 补齐。当前环境下 Fandom API 曾返回 402，BWIKI 可用但单张响应较慢；这些只是当次网络观察，换环境后应先抽样测试，不要把某个站点永远判死。
4. **超限图逐档压缩，不设最小体积。** 624 张候选中有 23 张源文件达到或超过 1,000,000 字节；使用 WebP 从高质量档开始逐档下调，首次低于上限即停止，并完整解码和目视检查。其他已低于上限的图保留源字节。若降到可接受质量仍超限，当时的做法是先找更合适的源图或裁掉不含人物的空白边缘，不放大凑体积，也不裁掉角色关键部位。**现行规则已改为先裁后压**（人物本体必须完整，伸出的武器和特效可以裁掉），见第九节。
5. **批量图也要看画面。** Pillow 全量解码用来发现截断和损坏；另做分组缩略图检查人物是否完整、是否拿错角色、透明层是否缺块。本批缩略图筛查没有发现明显模糊图，因此没有用修复工具。遇到模糊图时先找更清晰源图；仍无结果再评估修复，并复核眼睛颜色、脸部和服装细节。

### 后续构图复核：贝奇图片缺头（2026-11-13）

**发现。** Grok 指出仓库的 `贝奇.png` 是残图，复核属实：文件 503,315 字节、606×755，Pillow 可以完整解码，仓库结构检查也通过，但画面上边缘从上身开始，头脸完全不在图内。上游默认资源 `paintings/beiqi.webp` 也是同一截幅；这是来源构图本身的问题，不是下载截断。

**修正。** 改用 BWIKI 的[贝奇官方海报](https://wiki.biligame.com/blhx/%E6%96%87%E4%BB%B6:%E8%B4%9D%E5%A5%87%E5%AE%98%E6%96%B9%E6%B5%B7%E6%8A%A5.jpg)，原图 840×1138、1,178,348 字节，完整呈现头脸、服装和舰装。转成质量 98 WebP，保留 840×1138 原尺寸，文件 582,858 字节；已替换为 `贝奇.webp` 并通过完整解码及仓库检查。来源是官方宣传海报，带背景和少量文字，但角色主体清晰完整，适合当前视觉识别用途。

**教训。** 碧蓝航线早先的 263 张旧图当时只做了字节和格式验证，这张漏掉了构图缺失。批量图验收应分成两关：完整解码排除文件损坏，缩略图目视检查排除错图、缺头缺身和主体太小。人物识别需要眼睛颜色时，缺少头脸的图不能因文件完整而勾选。

### 碧蓝航线全量缩略图复核纠错（2026-11-13）

**复核缘由。** Grok 从 887 张中随机抽查 40 张，指出旗风、山风、文琴佐·焦贝蒂、摩尔曼斯克 4 张缺脸。此前虽然已生成全量图库，但没有实际完成逐页目视；把“图库已生成”当作“构图已审完”是流程错误。本轮对 887 张缩略图按每页 48 张重新扫过，共 19 页，四张问题图均确认属实。

**本轮新增的明确问题图。** 总览还发现：确捷（#188）为严重碎片拼接；纳希莫夫海军上将（#626）有大面积横向拖影和缺块；大胆（#668）头脸区域缺失；香槟（#678）只剩分散碎片，不能作为角色立绘使用。另有两张需要核对来源和素材类型：大凤（μ兵装）（#315）主要是舞台场景与屏幕画面，没有完整人物立绘；白雪（#392）画面主要是白兔和雪花，没有清楚的人物主体。后两项先列为选图疑点，不直接判为文件损坏。

**根因线索。** 所列异常文件都能被 Pillow 完整解码并通过文件大小检查，所以不能归因于传输截断。与上游逐字节相同的资源为：山风 `paintings/shanfeng.webp`、文琴佐·焦贝蒂 `paintings/wenqinzuojiaobeidi.webp`、摩尔曼斯克 `paintings/moermansike.webp`、确捷 `paintings/quejie.webp`、纳希莫夫海军上将 `paintings/naximofu_rw.webp`、大胆 `paintings/dadan_rw.webp`、香槟 `paintings/xiangbin.webp`。这些问题已存在于所选图源或图源变体中，下载和本地保存的完整性检查不会发现。旗风是仓库此前保留的旧图，与上游默认文件不相同，来源问题仍待追查。

本轮先完成审查和留档，尚未替换图片或调整清单状态；后续须找到并核对完整、对应角色的来源图后再修正。

**检查规则修正。** 文件解码、CRC、尺寸和体积检查仍负责发现字节损坏；顶部边缘启发式只查特定的贴边裁切，3 条提示不能代表只有 3 张有风险。碎片拼接、内部透明缺口、主体缺脸及选错素材要靠全量缩略图视觉筛查发现。图库必须实际逐页扫完并记录完成情况；“已生成”不能记成“已复核”。疑似图点击打开原图，再与可信来源或同角色其他立绘比对。可选的人脸检测或视觉模型只能作预筛提示，不能自动放行或自动判错。

**Grok 结构预筛补充与修复。** 用户提供的高对比透明区审查图列出 27 个候选，标签只作待核提示。原图复核确认其中有透明缺口、直切、错乱和误选场景／背景等问题；另把此前发现的纳希莫夫海军上将横向拖影一并修复。后续全图复核又发现纪伊只剩舰装、没有人物，也已更换。共替换 29 张：优先使用 BWiki 对应角色的完整立绘，只有“立绘”本身是 350×525 缩略图的少数角色才改用同形态官方海报。完整名单、来源、压缩和验收结果见[碧蓝航线立绘修复记录](碧蓝航线立绘修复记录.md)。这次修复的是已知问题，不代表其余图片已全部通过内容审查。

### 构图复核工具（2026-11-13）

`tools/audit_framing.py` 根据 `00-清单.md` 中的已勾选项，为每部作品生成本地 HTML 缩略图图库，默认每页 48 张，点击缩略图可看原图。它覆盖旧图和新图，避免只检查本次下载项；无法解码或缺失的文件会列入错误区。对于带透明通道、顶部 2% 内有一行明显主体覆盖超过 40% 画宽的图片，会加橙框作为复核提示；极淡的抗锯齿边缘不计入。该启发式会把头发、舰装、特效或有意贴边构图当成风险，不能自动判残图，也不会修改清单或图片。它是人工总览的辅助，不替代构图判断；有不透明背景的裁切图主要靠总览发现。

运行方式：

```bash
python3 tools/audit_framing.py images/碧蓝航线
```

打开脚本输出的 `.image-audit/<作品名>/index.html`，逐页扫过所有缩略图；橙色提示项优先复核，其他图也要扫过。输出目录已加入 `.gitignore`，不会混进图片仓库。

### 残图自动检查工具（2026-11-13）

缩略图总览要人一页页看，图一多既费时间也费 token。`tools/defect_check.py` 先自动筛一遍，人只看被标记的图：

```bash
python3 -m pip install pillow numpy opencv-python-headless
python3 tools/defect_check.py 碧蓝航线 --sheet --all-levels   # 不写作品名就检查全部
```

结果写到 `out/defect_check/`（已加入 .gitignore，不提交）：`summary.md` 是按作品分组的名单和原因，`results.json` 是完整数据，`<作品>-高-01.jpg`、`<作品>-低-01.jpg` 是联系表（品红底，透明空洞一眼可见；绿线是检测到的裁切直线，蓝框是检测到的脸）。脚本只读，退出码总是 0；加 `--strict` 时有“高”结果返回 1。`--workers` 控制并行进程数，1000 张图约 1 分钟。

它看的信号：

- **直线裁切 / 矩形空洞（高）**：透明边缘上有一条完全水平或竖直、过渡像素逐像素一致的长直线。手绘轮廓不会这样，拆包时缺了图层（脸、头、上半身）才会留下这种矩形切口。碧蓝航线的旗风、山风、文琴佐·焦贝蒂、摩尔曼斯克、旧版贝奇都属于这一类。紧贴画布边缘的切口不算，那是画布本身的边。
- **没有人物（低）**：动漫人脸检测器没找到脸，而且主体里几乎没有肤色，常见于只剩舞台、特效或舰装图层的错图（如 μ兵装的舞台图）。
- **找不到脸（低）**：只有人脸检测器没认出来。侧脸、遮脸、脸很小的完整立绘也会触发，误报最多，扫一眼即可。
- 顶边截断、主体最上方很宽等弱信号只作附带说明。

2026-11-13 全仓库跑了一遍：1033 张，“高” 19 张里 17 张是真残图，“低” 100 张里 10 张是真残图，确认的 27 张都在碧蓝航线；星穹铁道和原神没有残图。已知漏报：只剩舞台、但检测器误认出“脸”的图（如恶毒（μ兵装））。所以它只是缩小人工复核范围，不代替 `audit_framing.py` 的总览；被标记的图要打开确认后再决定是否取消勾选。

确认的 28 张（含恶毒（μ兵装））已在 2026-11-13 取消勾选并删除，清单行尾用「备注：」写明问题，名单见 `images/碧蓝航线/00-清单.md` 末尾「待重找残图」。它们都是客户端拆包的分层立绘缺了脸、头或人物图层；重找时改用 wiki 上的完整立绘，勾选前先跑 `defect_check.py`。

### 视觉模型预筛拼图（2026-11-13）

构图复核工具现在还会输出编号联系表：透明像素显示为亮洋红色，编号对应表包含简体中文名和图片路径，并附有可直接交给视觉模型的审查提示。建议把每页拼图分批交给视觉模型，只让它返回疑似编号和理由；再按编号表打开原图、核对人物是否缺脸或整图是否选错。洋红缺口、直切和无角色主体很醒目，但模型输出仍是候选清单，不是自动验收结果。全库复核还要记录实际审过的页数，生成拼图不等于复核完成。

### 星穹铁道收集记录（2026-11-13）

**结果。** 按 `images/星穹铁道/00-清单.md` 原有 60 个角色及形态逐一找图后，又补入最新实装角色星神★阿哈；清单现有 61 项，61 张全部下载、完成 WebP 转换并通过完整解码。不同形态（如三月七存护／巡猎、姬子启行、知更鸟晴歌、银狼 LV.999）分别匹配，没有复用基础形态。最终文件保持原图尺寸：60 张为 2048×2048，忘归人为 1080×1920；文件大小 561,772 至 998,248 字节，没有设最低体积。

**图源与下载。** 通过 BWIKI 星穹铁道站的 MediaWiki 文件命名空间搜索「立绘」，再查对应文件的 `imageinfo` 取得 `patchwiki.biligame.com` 直链。61 个来源文件都先写成二进制文件，再用 Pillow 完整解码并核对接口返回的字节数和分辨率；使用 3 个并发直接下载，整批顺利完成。API 在重复查询过多时可能返回 567，后续可先缓存文件名、直链和尺寸，再直接下载媒体 URL，避免反复搜同一批条目。不同作品或网络环境下仍应先抽样测速，不把本次速度当成长期保证。

**超限图处理。** 来源大多是 2.4–6.5 MB 的 PNG。用 WebP `method=6`、保留原分辨率和透明通道，从质量 98 开始逐档下调，到小于 1,000,000 字节即停止；大部分图片保持质量 98。飞霄在质量 90 时仍略超限，质量 88 后为 979,966 字节；遐蝶在质量 86 时为 1,045,824 字节，质量 84 后为 993,988 字节。遐蝶在 1:1 对照图上复核了眼睛、脸部及服装细节，仍清楚，因此无需缩小、裁掉人物部分或使用 AI 修复。这个例子说明：轻微超限时先尝试小幅调整编码质量并目视复核；不要用低于 1 MB 的阈值替代清晰度判断，也不要只看缩略图决定。

**选图注意。** 忘归人优先采用 `忘归人立绘3.jpg`（1080×1920，1,985,913 字节）：画面带有宣传字，但人物全身较大且清楚；横向的 `忘归人立绘2.png` 中人物更小、背景和文字更多，不适合本次识别用途。若基础文件名或默认结果只是横幅／宣传卡，继续查找角色主体更大的版本，不要因为文件名命中就停止。最终 60 张缩略图逐项核对后没有发现明显错配或糊图。

**最新角色增补。** 2026-11-13 对照 BWIKI 当前角色页，确认星神★阿哈于 4.7 实装；从 4 个候选中选 `星神★阿哈立绘.png`（2048×2048，4,338,141 字节）。它是无宣传文字的透明背景正方形立绘，人物比横幅和宣传海报更突出。转成保留透明通道的 WebP，质量 88、973,948 字节；眼睛、脸部和服饰细节经原图对照仍清楚。清单行保留角色全名，用「阿哈」作别名，文件名用中文 `星神阿哈.webp`。[BWIKI 角色页](https://wiki.biligame.com/sr/%E6%98%9F%E7%A5%9E%E2%98%85%E9%98%BF%E5%93%88)

## 三、原神的经验：稳定拿到完整原图

1. **优先用官方或 Wiki 的图片直链。** 原神的立绘可以通过 BWIKI 的 MediaWiki 接口查到直链，再从 `patchwiki.biligame.com` 的国内 CDN 下载，又快又稳：
   `https://wiki.biligame.com/ys/api.php?action=query&titles=File:<角色名>立绘.png&prop=imageinfo&iiprop=url&format=json`
   碧蓝航线这次的恢复源是 [AzurLane-AssetDownloader 提取的立绘仓库](https://github.com/iujab/azurlane-images)及其配套的 [Lycoris-AzurAPI 舰船数据](https://github.com/iujab/Lycoris-AzurAPI)。数据文件将舰船 ID、简体中文名和默认立绘直链对应起来；旧清单 887 个 ID 均能映射，抽查的 3 张现存图与上游图解码后像素完全相同，5 张待恢复样本也通过下载与完整解码。恢复时用 ID 仅作临时映射，仓库文件名统一使用简体中文角色名。其他作品同理：萌娘百科、BWIKI 对应的游戏站、Fandom（可加 `format=original` 获取原图）、官网和官方社交账号。不要用 AI 图和 Pinterest。
2. **从 GitHub 拉大文件要小心。** GitHub 内容接口返回 JSON 时只内嵌 1MB 以下的文件；大文件要用 raw 方式，且容易中途断开。能走 Wiki 或 CDN 就别走 GitHub 接口。
3. **控制并发。** 同时开太多请求会被限流或断连。2 到 3 个并发、请求之间停 1 秒比较稳。下载失败就重试，不要把半截文件留下。
4. **先缓存索引。** 需要从某个仓库挑文件时，先一次拉下整棵目录树存到本地，再按需下载，避免反复查询。
5. **网络不稳时的 git 设置（Windows 国内网络）。** `git config --global http.sslBackend schannel`，克隆时加 `--filter=blob:none`。

## 四、调整大小和验证（可直接用）

```python
from pathlib import Path
from PIL import Image

MAX_EXCLUSIVE = 1_000_000

def verify(path: Path) -> bool:
    try:
        with Image.open(path) as im:
            im.load()  # 完整解码，截断或损坏会在这里报错
        return path.stat().st_size < MAX_EXCLUSIVE
    except Exception:
        return False

def fit(src: Path, dst_stem: Path) -> Path:
    """保持清晰度并确保最终文件小于 1 MB；不设最低体积。

    调用前应先按第九节完成裁剪（人物本体完整，武器和特效可裁）。
    本函数只负责裁完之后的压缩，不再把裁切当作最后手段。
    """
    im = Image.open(src)
    im.load()
    if src.stat().st_size < MAX_EXCLUSIVE:
        return src
    has_alpha = im.mode in ("RGBA", "LA", "P")
    out = dst_stem.with_suffix(".webp")
    img = im if has_alpha else im.convert("RGB")
    for q in (98, 97, 96, 95, 94, 92, 90, 88, 86, 84, 82, 80):
        img.save(out, format="WEBP", quality=q, method=6, exact=True)
        size = out.stat().st_size
        if size < MAX_EXCLUSIVE:
            break
    if size >= MAX_EXCLUSIVE:
        raise ValueError(f"质量 80 仍超出 1 MB，回到第九节检查是否还可安全裁剪，或另找更合适的源图，不要继续盲目降质：{src}")
    if q < 90:
        print(f"需要目视复核低于质量 90 的图片：{out}")
    assert verify(out), f"验证失败：{out}"
    return out
```

## 五、清单约定（容易写错的地方）

- 勾选格式是 `- [x] [角色名](文件名.ext)`；文件名带空格或括号时用尖括号 `[角色名](<文件名.ext>)`。
- 同一角色的不同版本是清单里单独的一行，名字写成 `三月七（巡猎）`（全角括号在链接文字里面），不要把版本写在链接外面。
- 不要改动清单里的角色名和「别名：」。名字需要修正时单独说明。
- 文件名使用简体中文角色名，便于人工检索和与任务清单比对；编号只用于临时核对来源，不作为最终文件名。
- 没收到图的角色保持 `- [ ]`，不要用占位图凑数。

## 六、建议的工作流程

1. 读 `README.md`、本文档和目标作品的 `00-清单.md`。
2. 找到稳定的图源，先拿 3 到 5 个角色试跑：下载、调整大小、完整解码验证。
3. 分批下载；每张先完成二进制写盘、完整解码和人物清晰度检查，再勾选。不要因为分批而把未验证图片标为已收集。
4. 提交前跑 `tools/check.py`，并对本次图片做 Pillow 完整解码。
5. 汇报时写清楚：收了多少、剩多少、遇到什么问题、怎么解决的。有新的坑，补充到这份文档里。

### 收集原图的人（GPT、Gemini 等）要做的

1. 把原图放进对应作品的子文件夹，**不压缩、不改尺寸、不转格式**，保持来源的原样。
2. 文件名就用清单里的角色名，例如 `温迪.png`、`三月七（巡猎）.png`，扩展名保持原图的格式。
3. 上传前先用 Pillow 完整打开一次，确认图片完整（第一节第 1 条）。用连接器上传时尤其要小心，大文件经过 base64 文本可能被截断，上传后对比一下云盘上显示的大小和本地文件大小。
4. 原图没有大小上限，越清晰越好；人物太小或太糊的不要。
5. 不要改动仓库里的清单勾选状态，勾选由压缩环节负责。

### 压缩环节要做的

从原图库取图，压成长边约 1600 到 2000 像素的高质量图片（有透明背景的用 WebP），验证能打开后放进仓库对应文件夹，在清单里勾选并写好链接，跑检查后提交。原图库里没有、但仓库里已有的图保持不动。

## 八、皮肤立绘收录规则

- 挑着收，不要全量收。只收写小说时常用的皮肤（泳装、礼服、正月、圣诞等），每个角色一两套即可。
- 命名使用「角色名（皮肤名）」格式，例如 `拉菲（泳装）`。
- 在作品 `00-清单.md` 里单独开「## 皮肤」小节，和本体分开打勾，不要把皮肤混进本体的进度。
- 图片标准与本体相同：清晰，眼睛颜色和瞳孔花纹可辨，全身；透明边可以裁掉。
- 单张必须小于 1,000,000 字节。
- 皮肤数量多的作品（例如碧蓝航线）放在独立仓库；单个仓库接近 1 GB 时再开新仓库。

## 九、先裁后压

处理顺序是**先裁剪、再压缩**，不要先把大图画质压低再裁。很多立绘特效大、人物相对小，先压缩会把人物一起压糊，先裁掉多余部分后再压，人物更容易保持质量 98 且仍小于 1,000,000 字节。

- **人物本体必须完整**：头（含头发、耳朵、头顶光环）、脸、躯干、手臂、手、腿、脚、服装、头发。
- **武器和特效可以裁掉**：伸出本体之外的武器、技能特效、大场景或随从，不必为了保留它们而留下大片空白。
- 去掉透明空白边和多余背景，裁框四周留约 3%–5% 的边距，人物居中。禁止放大。
- 裁完后如果仍然达到或超过 1,000,000 字节，再按第四节用 WebP quality 从 98 逐档下调（`method=6`，保留透明通道）。
- **带背景的图**不能全自动裁。脚本给出的裁剪框要先在预览联系表上确认，确认前不要加 `--apply`。看不准的图会标成 `manual`，工具不会自动改写这些文件。

工具默认只读，预览写到已加入 `.gitignore` 的 `out/crop_preview/`（品红底，左侧红框是建议裁剪范围，右侧是裁后效果）：

```bash
python3 tools/crop_character.py images/<作品>          # 只读，生成对照表和 JSON
python3 tools/crop_character.py images/<作品> --apply  # 只写入 status=auto 的图；manual 不会被改
```

透明底的图可以批量预览后应用；带不透明背景的图必须先打开联系表看红框，再决定要不要裁。
