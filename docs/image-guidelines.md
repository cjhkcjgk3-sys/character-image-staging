# 角色图片收集与整理方法

本规则供用户、模型或 Agent 收集角色图片时使用。目标是让酒馆中的模型能看清角色外观，并能按名单找到正确图片。默认先保持简单：**一个作品一个文件夹，图片使用中文角色名；优先保证人物清晰，大小以约 1 MB 为目标。**

## 一、先确认找的是谁

1. 以名单中的**作品名和角色名**查找，保留名单原文；不要仅凭相同名字断定是同一角色。
2. 默认寻找该角色的**初始形象 / 默认立绘**。换装、其他时代、动画版或同人图要明确标记，不能代替默认版本。
3. 优先使用来源清楚、能回查到具体作品和角色的官方资料或可靠作品页面。搜索结果只是候选，要打开页面并实际查看图片。
4. 一个角色有多个可能的形象、版本或来源时，先列候选请用户选择；找不到合适的图则记为待处理，不借用其他角色的图片。

## 二、怎样才算适合作为外观参考

- 收集的是**以角色为主体的图片**。优先找独立角色立绘、透明背景或背景简单的角色图，让人物在画面中足够大；不要把纯背景图、人物很小的风景图当作角色图。
- 优先选择人物尽可能从头到脚可见、无明显模糊或大片遮挡的图片；脸部、发型、眼睛、衣服、鞋袜和属于角色造型的装备应尽量清楚。人物主体与细节比画面背景更重要。
- 找到的图如果有多余的背景、边框或大段文字，可以在**完整保留人物、发型、衣着和关键装备**的前提下裁掉这些多余区域，并记录裁剪。不能为了缩小文件截掉人物部位，也不要用抠图或生成内容改变衣服与外观；边界拿不准时保留原图并标记待确认。
- 不要仅凭“立绘”这个文件名判断：本次原神试收集里的部分方图被裁掉了下半身，竖版宣传图又可能被文字或动作遮挡。官方图本身有遮挡时如实说明，不能宣称遮挡处已经看清。
- 对比原图与处理后的图，放大检查眼睛、头发边缘、衣物配色和小饰品；如果这些细节明显受损，就调整压缩参数或更换来源。
- 没有独立立绘时，可把人物清楚的游戏截图作为**单独标注的候选**，不能冒充官方立绘。例如这次的芙卡洛斯图片是剧情截图。

## 三、大小、清晰度与格式

1. **目标大小：每张约 1 MB（1,000,000 字节），优先保证人物细节。**这是便于传输和存储的目标，不是硬上限；清楚的 200 KB 图片不必放大或增重。
2. 比较同一角色和形象的候选图时，先看人物是否完整，以及眼睛、发型和衣服是否清楚。如果 1 MB 图已经清楚、2 MB 图没有明显改善，就选 1 MB 图；如果 2 MB 图确实能看清 1 MB 图丢失的关键细节，就选 2 MB 图。**不能只因为文件较大就认定画质更好。**
3. 遇到清晰的较大图片，先尝试制作合适的较小副本；压缩到约 1 MB 后细节明显变差，就保留更清楚的较大版本，不为了达标继续压坏。2 MB 是可接受的例子，不是新的硬上限；图片仍很大且不好取舍时，列出大小与区别供用户决定。记录最终大小与必要的处理说明。
4. 已经清晰、大小合适的 JPEG、PNG 或 WebP，优先保留原文件。不要只为了统一后缀而重新压缩。
5. 超大原图先保留可回查的来源，再压缩副本；如有需要可按第二节裁掉多余背景，但不能裁掉角色，缩放时也不能改变长宽比例。优先尝试 WebP，尽量保留透明背景与原始分辨率；无损可达合适大小时优先无损，否则使用视觉质量较高的有损压缩。
6. 例如 10 MB 以上的图片，必要时按第二节裁掉合适的多余背景，并尝试保持人物原尺寸转换为 WebP；还太大时逐步调整压缩质量，必要时再适度缩小。竖版人物图可先以**长边约 1,600～2,400 像素**作为试验范围；这只是起点，画面是否看得清比固定像素数更重要。不凭插值放大小图冒充高清。
7. 压缩后需要能正常解码，比较前后尺寸、文件大小与外观；清单记录最终格式、大小或处理说明、来源和哈希。
8. 根据图片**实际字节格式**确定扩展名与 `mime_type`，不要只看原网址或服务器声称的类型。本次就遇到过网址以 `.png` 结尾、内容实际是 JPEG 的图片。

WebP 支持透明背景；目标酒馆 1.19.0 的公开源码将 `webp` 列为允许的媒体格式，但用户手机的导入扩展与模型请求仍需实测。若实际环境不支持，再转换成合适的 PNG 或 JPEG，透明背景不能静默变成错误颜色。

## 四、目录怎么放

默认按**作品**建一层，不先按地区、阵营或角色各自再建文件夹：

```text
images/
├── 原神/
│   ├── 清单.md
│   ├── 温迪.jpg
│   ├── 钟离.webp
│   ├── 芙宁娜.webp
│   ├── 芙卡洛斯.webp
│   └── 角色甲（演出服）.webp
└── 另一部作品/
    └── 角色乙.png
```

这只是命名示意，图片的实际格式和可用状态以清单为准。默认不再分“璃月 / 枫丹”：角色可能跨地区、改变身份或属于多个阵营，过早细分会增加查找和重复保存的麻烦。

只有当某一作品的图片确实多到影响浏览、工具性能或用户明确需要分类时，再按适合该作品的方式增加一层，并同步更新清单；不要提前为每部作品建立空分类。导入器应以 `catalog/catalog.json` 的路径为准，而非只依赖扫描某个目录。GitHub Contents API 对单目录列表有 1,000 项上限；规模超过时可按清单逐项读取或使用树接口。

每个作品目录放一份 `清单.md`，先把用户确定范围内的全部待收集角色逐行写成 `作品名·角色名`，空框表示待收集。有多个形象时写明版本。Agent 从空框开始查找；图片存入且与目标角色和版本对应后打勾，并可将名字链接到图片。找不到、版本不明确或只有候选时保留空框，在行尾注明原因。打勾表示目标图片已存入仓库，是否通过质量复核仍以 `catalog/catalog.json` 为准。图片或其机器记录变更时，由执行任务的人或 Agent 同步更新；目前尚未实现自动同步。

例如：

```markdown
- [ ] 原神·待收集角色
- [x] [原神·温迪](温迪.jpg)
```

清单只保存文字、勾选和图片链接，不嵌入图片数据；一百多个名字仍只是一个很小的文本文件。尚未收集的名字可以先写入清单，不需要先创建图片或填写完整的机器记录。

## 五、中文文件名怎么写

1. 文件名直接使用**中文角色名**，例如 `温迪.jpg`、`芙宁娜.webp`，便于用户和 Agent 统一检索；不要用 `001.png`、`IMG_0001.jpg` 或英文编号代替名字。原名含英文或数字时，优先采用通用中文译名；没有可靠译名则待用户确认，清单仍保留实际名单原文。扩展名如 `.jpg`、`.png` 和 `.webp` 保留为对应格式。
2. 每名角色的默认立绘直接叫 `角色名.扩展名`；有其他版本时，用能看懂的中文名称区分，例如 `角色甲（演出服）.webp`。不要用“版本1”“版本2”代替具体含义。
3. 不同作品的同名角色放在各自作品文件夹。若同一作品内仍然同名，用用户认可的中文称谓或身份区分；无法确定时请用户选择，不靠数字随意区分。
4. 名称中的斜杠、冒号等可能导致路径问题的字符，使用清晰的中文标点或经确认的中文别名；处理后如果重名，停止并人工区分，不能覆盖已有图片。
5. 文件名方便人看；**实际批量匹配以清单中的完整 `roster_name` 为准**。例如文件是 `images/原神/温迪.jpg`，名单可能写成 `温迪（原神）`，两者通过清单对应。要使用用户酒馆里的实际名单原文，不擅自猜测其格式或扫描提示词中的任意名字。
6. 清单内部的稳定 `id` 是给程序使用的标识，不是图片文件名；不会要求用户把图片改成英文或数字名称。

## 六、一张图片完成时

按顺序检查：**角色与作品对上 → 图片类型和版本清楚 → 实际看过图 → 清晰度和大小合适 → 中文命名 → 来源及哈希写入清单。**

身份、版本或图片质量不明确时，标记 `needs_review`；下载失败标记 `failed`。只有实际文件存在并完成上述检查，才能按清单约定标记 `ready`。原神测试图片已存入仓库，但尚待按本规则复核；仓库中有文件不代表图片已经导入酒馆。

现有的清单检查脚本能检查字段，以及 `ready` 图片的文件存在、文件头和可选的哈希；`needs_review` 图片的文件和哈希需要单独检查。脚本不会自动判断中文命名、1 MB 大小、图片内容或清晰度，这些仍需在收集时检查。
