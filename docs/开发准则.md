# 开发准则（所有 AI 模型通用）

适用于小说自动生成器（Novel-Auto-Generator）和三个角色图片仓库里的代码、工具、界面与规则文档。GPT、Gemini、Claude、Grok 等任何模型都按这份准则开发；`AGENTS.md`、`GEMINI.md`、`CLAUDE.md` 都指向这里。四个仓库里的这份文件内容相同。

每个模型都有自己的习惯：喜欢把规格做得“严谨”、喜欢另起炉灶、喜欢一刀切。用户不纠正，就会出现步骤繁琐、界面突兀、重复造轮子、规则死板。下面先列每次都要做到的基础准则，再列按优先级排列的五条核心原则，冲突时排在前面的优先。

## 基础准则（每次开发都要做到）

1. **先读懂再动手**：先读相关代码和文档，弄清现在怎么做的，别凭猜测重写。
2. **改动要小**：只改需要改的地方，不顺手重构、不乱改格式，便于回退。
3. **不破坏现有功能**：改完跑测试；旧数据、旧配置继续可用，实在不兼容要给出清楚提示。
4. **简单优先**：能用简单办法解决就不上复杂设计，不为想象中的需求提前铺功能。
5. **出错要说人话**：报错要让用户看得懂并说明下一步怎么办，不能悄悄失败。
6. **命名一致**：变量名、文件名、界面用词与现有的一致，同一个东西不叫两个名字。
7. **做完要验证**：说“完成”之前实际跑一遍；没测到的地方明说，不报喜不报忧。
8. **不确定就问，能定的自己定**：只在会严重影响结果时问用户，小事按合理默认值处理。
9. **文档跟着代码走**：功能一改，README、CHANGELOG 和规则文档同步更新。
10. **以用户请求为准**：用户说做几件就做几件，不强求一次只做一件。

## 核心原则（按优先级）

### 1. 易用性第一

- 最常用的操作用最少的步骤完成；默认值要让大多数情况不用改。
- 能自动判断的就不让用户选。只有真正需要取舍、而且选错代价大时才问。
- 不为假想的需求加开关、选项和确认框。看起来设计严谨、却处处让用户选择的方案，算失败。

例：1.15.0 导入作品 ZIP 时自动保存清单里的名字，用户只要“打开 → 勾选 → 加入名单”；已在名单里的名字自动跳过，不弹窗问“是否跳过重复”。缩略图曾提议加“改成文件夹图标”的开关，用户确认缩略图不影响流畅度后就没加。

### 2. UI 一致性

- 新界面先找插件里同类元素照着用，不用浏览器默认样式，不自造颜色和尺寸：按钮 `menu_button`，设置行 `nag-setting-item`，勾选框 `nag-checkbox-label`（绿色 `#8bc34a`），状态标签 `nag-status-badge`，弹窗 `nag-modal`／`nag-modal-header`／`nag-modal-close`，折叠区 `nag-collapsible`，名单行 `nag-role-status-row`。
- 颜色要在酒馆默认暗色主题下看得清。改完在手机宽度（约 390 px）、暗色主题下截图自查。

例：1.15.0 新界面出现浏览器默认的蓝色勾选框；“无图”虚线框用了半透明黑边框色，在暗色主题下几乎看不见；全屏看图的“不用图”按钮在黑色遮罩上看不清，关闭按钮也和插件弹窗不一样。用户一眼就觉得突兀，1.15.1 全部改回插件已有样式。这类问题应该在开发时自己发现。

### 3. 代码复用，不重复造轮子

- 动手前先搜：用 `rg` 查函数名、关键词和类名，读相关模块的导出。
- 有现成的就直接用，或者加参数、加分支来扩展，不平行再写一套。宿主（酒馆）已有的接口优先于自己实现。
- 确实没有合适的再写新的，放进对应模块，命名和风格与周围代码一致。
- 同一规则只保留一份实现和一份权威说明。图片仓库三份 `tools/` 是同一份代码，改一处同步三处。

例：1.13.0 图片库直接复用酒馆现有的图片上传、删除、ZIP 解析和生成拦截接口，没有增加服务或依赖。反例：图片仓库 `tools/check.py` 的 `match_name` 带包含匹配，和生成器实际的匹配规则不同，文档却让人参考它，结果两边说法打架；现在以生成器实现为准，`check.py` 只做 CI 提示。

### 4. 兼容要有弹性，该严格的地方要严格

判断方法：**放宽“怎么写”，不放宽“是谁”。**

- 输入的写法可以宽松：全角／半角、空格、标点、括号、作品名前后缀、压缩包目录层级、文件名编码。合理的写法尽量都认。
- 结果出错代价大、用户又不容易发现时要严格：给错图、认错角色、覆盖或删除数据、花钱。宁可不做并说明原因，也不要猜。

该宽的例子：v1（GPT 开发）要求完整名字逐字相同，`安比（绝区零）改` 这类写法对不上；1.14.0 改成“作品名可选 + 角色名 + 备注”，只忽略全／半角、括号、标点和空格，`安比（绝区零）改`、`绝区零安比改`、`安比改` 都能对上 `安比（改）`。清单放在 ZIP 根目录（download-directory 直接打的包）、中文 Windows 压缩工具写的 GBK 文件名也都能导入。

该严的例子：写了备注但没有对应形态图时按无图处理，不拿本体图顶替；不做包含或模糊匹配（`小安比` 不配 `安比`）；有多张候选时不用图。图片仓库单图严格小于 1,000,000 字节，人物本体必须完整。

反例：早期规则把单图体积定为 500 KB～2 MB，小图被放大凑体积。体积本来只该有上限，不该有下限，这就是把不该绝对的东西定死了。

### 5. 按用户意图做，不死抠字面规格

- 蓝图和需求文档是方向，不是逐字合同。实现前先用一句话复述“用户最终怎么用”，再按这个目标取舍。
- 字面要求和明显意图冲突时按意图做，并在汇报里说明差异。拿不准时问一个具体问题，不要做一个让用户自己选的复杂方案。

例：蓝图写“一次导入 ZIP”，用户的意思是一次上传、像手机相册一样按需打开，而不是一次把整包读进内存。1.14.0 改成按需读取后，明日方舟包导入时的内存峰值从约 661 MB 降到 141 MB。用户要“名单跟着压缩包走”，就直接读包里已有的 `00-清单.md`，不另造名单文件。用户是在手机上直接下载 ZIP，不一定经过 Windows，所以导入要兼容各种打包方式。

## 常见 AI 误区（用户实际遇到过的）

- 规格写得面面俱到，用户每一步都要选（违反第 1 条）。
- 按自己的习惯写新界面，不看插件已有样式（违反第 2 条）。
- 不搜现有代码，平行写一套；或者同一规则写两份，后来互相矛盾（违反第 3 条）。
- 规则一刀切：要么要求全名逐字相同，要么什么都模糊匹配（违反第 4 条）。
- 把蓝图当合同逐字实现，忽略用户真实的使用场景（违反第 5 条）。
- 把“图库已生成”当成“已复核”，把“能解码”当成“画面完整”，把没实测过的功能说成已验证。
- 为了让检查通过而修改数据，例如补文件结尾、用占位图凑数。
- 规则改了，文档、README 和记录却没跟着改，留下互相矛盾的旧说法。

## 提交前自查

1. 最常用的操作要几步？能不能少一步？有没有本可以自动判断、却让用户选的地方？
2. 新界面用的是插件已有类名吗？在手机宽度和暗色主题下看过吗？
3. 搜过现有函数和组件吗？有没有重复实现，或者和别处的规则说法冲突？
4. 输入的各种写法都兼容了吗？会给出错误结果的地方是否足够严格？
5. 和用户原话的意图对得上吗？和蓝图有偏差的地方写进汇报了吗？
6. 检查都跑了吗？生成器：`npm run verify`，并更新 `CHANGELOG.md` 和版本号（已有的失败测试要说明，不能新增失败）。图片仓库：`python3 -m unittest discover -q tests` 和 `python3 tools/check.py images/<作品>`。
7. 相关文档和规则同步更新了吗？汇报里是否写清了哪些实测过、哪些还没在手机或真实酒馆里试过？
